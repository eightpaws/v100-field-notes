# V100-150 — 27B PXQN: 8k context and two clients on one 16 GB card

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-148 showed the 27B PXQN checkpoint using 14 583 MiB at a 4k context, which leaves no room for either a longer context or a second slot. Does 8192 start at all, and does a second client raise total throughput by the 1.6× that a dense model this size would need to be worth serving in parallel?

**Environment.**

| Component | Value |
|---|---|
| GPU | Tesla V100-SXM2 16 GB, compute capability 7.0 |
| Driver | 580.178.04, CUDA toolkit 12.9 (installed without root) |
| Engine | PXA 4.0.4, `pxa-launch --engine llama` (llama.cpp server underneath) |
| Model | poisonxa/Qwen3.8-27B-PXQN-OneCard, 12.625 GiB, 3.969 bits per weight |
| Host | Ubuntu 24.04, 24 vCPU, 94 GiB RAM |
| Workload | one and two simultaneous clients, 128 generated tokens, temperature 0, thinking disabled |

**Commands.**

```bash
/srv/media/ai-cache/downloads/pxaimg/root/opt/pxa/dist/pxa-launch \
  -m /srv/media/ai-cache/downloads/qwen38-27b-pxqn-onecard.gguf \
  --engine llama -c 8192 --np 2 --port 18096 --no-tui --no-interactive --yes
PORT=18096 TAG=8k_np2 NTOK=128 REPS=3 python3 /root/v150_harness.py
```

The second pass used the same driver with `-c 16384 --np 2` (8192 tokens per slot) and the run itself went through `bash /root/bin/v100-run.sh V100-150 -- bash /root/v150_driver.sh`. Two clients are released together by a `threading.Barrier`; each call is `/v1/chat/completions` with `max_tokens 128`.

**Result.**

| Configuration | Context per slot | Peak VRAM | Single client | Two clients, total | Scale |
|---|---|---|---|---|---|
| `-c 8192 --np 1` | 8192 | 14 850 MiB | 139.1 tok/s (97.1 first, 159.7-160.6 warm) | 115.3 tok/s (second call queued: 115.4 / 57.7) | 0.83× |
| `-c 8192 --np 2` | 4096 | not recorded | 109.2 tok/s | 91.4 tok/s, 101-119 per stream | 0.84× |
| `-c 16384 --np 2` | 8192 | 15 529 MiB | 101.6 tok/s | 81.7 tok/s, 82-103 per stream | 0.80× |

`--np` divides `-c`: at `-c 8192 --np 2` a client gets 4096 tokens, so "8k context with two clients" costs `-c 16384`, which does start and leaves about 615 MiB free.

**Verdict.** Negative: a 27B at 3.97 bits already saturates this card, so a second client costs 16-20 % of the throughput instead of adding the 1.6× the card would need, while the 8k context itself does fit (14 850 MiB peak at one slot, 15 529 MiB with two 8k slots).

**Result type.** Negative.

**Does not show.** Quality was not re-measured on these configurations (MBPP for this checkpoint is in V100-148); answers are 128 tokens with no tool calling and no growing context; the `-c 16384 --np 2` start was tried once, and 615 MiB of headroom may not survive a prompt that actually reaches 8k on both slots.
