# V100-150 — 27B PXQN: 8k context and two clients on one 16 GB card

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-148 showed the 27B PXQN checkpoint using 14 583 MiB at a 4k context, which leaves no room for either a longer context or a second slot. Does 8192 start at all, and does a second client raise total throughput by the 1.6× that a dense model this size would need to be worth serving in parallel?

**Environment.**

| Component | Value |
|---|---|
| GPU | Tesla V100-SXM2 16 GB, compute capability 7.0 |
| Driver | 580.178.04, CUDA toolkit 12.9 (installed without root) |
| Engine | PXA 4.0.4, `pxa-launch --engine llama` (llama.cpp server underneath) |
| Model | poisonxa/Qwen3.8-27B-PXQN-OneCard, 12.625 GiB, 3.969 bits per weight |
| Host | Ubuntu 24.04, 24 vCPU, 94 GiB RAM |
| Workload | one and two simultaneous clients, 128 generated tokens, temperature 0, thinking disabled |

**Commands.**

```bash
/srv/media/ai-cache/downloads/pxaimg/root/opt/pxa/dist/pxa-launch \
  -m /srv/media/ai-cache/downloads/qwen38-27b-pxqn-onecard.gguf \
  --engine llama -c 8192 --np 2 --port 18096 --no-tui --no-interactive --yes
PORT=18096 TAG=8k_np2 NTOK=128 REPS=3 python3 /root/v150_harness.py
```

The second pass used the same driver with `-c 16384 --np 2` (8192 tokens per slot) and the run itself went through `bash /root/bin/v100-run.sh V100-150 -- bash /root/v150_driver.sh`. Two clients are released together by a `threading.Barrier`; each call is `/v1/chat/completions` with `max_tokens 128`.

**Results.**

| Configuration | Context per slot | Peak VRAM | One client, decode | One client, end to end | Two clients, decode (sum) | Two clients, end to end | Per client, decode |
|---|---|---|---|---|---|---|---|
| `-c 8192 --np 1` (continuous batching) | 8192 | 14 850 MiB | 139.1 tok/s | 103.2 tok/s | 322.8 tok/s | 115.3 tok/s | 161.4 tok/s |
| `-c 8192 --np 2` | 4096 | not logged (engine plan estimate 14 634 MiB) | 109.2 tok/s | 86.2 tok/s | 207.8-220.3 tok/s | 90.8-91.8 tok/s | 104-110 tok/s |
| `-c 16384 --np 2` | 8192 | 15 529 MiB | 101.6 tok/s | 81.7 tok/s | 167.3-191.5 tok/s | 81.5-82.1 tok/s | 84-96 tok/s |

Decode speed is the server's own `timings.predicted_ms`; end-to-end speed is read off the wall clock and includes prefill and connection setup. Only numbers inside one column are comparable: in a 128-token answer a large share of the wall time is everything that is not decode.

`--np` divides `-c`: at `-c 8192 --np 2` a client gets 4096 tokens, so an 8k context per client costs `-c 16384`, which does start and leaves about 615 MiB free.

**Repeats.** n=3 per configuration: three single requests and three simultaneous pairs; peak VRAM is one start per configuration.

**Verdict.** Mixed. The 8k context per slot fits and a second client does not steal throughput: with `-c 8192 --np 1` each of two clients decodes at 161.4 tok/s, which is 2.3x the single-client decode, and with `-c 16384 --np 2` they still get 84-96 tok/s each. Read end to end on 128-token answers the gain is only 1.06-1.12x, because prefill and connection setup dominate such short answers. The first edition of this card reported "0.80-0.84x with two clients": that ratio divided a wall-clock aggregate by a server-side single measurement, so it measured the metric, not a throughput loss.

**Result type.** Mixed.

**Does not show.** Quality was not re-measured on these configurations (MBPP for this checkpoint is in V100-148); answers are 128 tokens, with no tool calling and no long prompt inside the request; the `-c 16384 --np 2` start was tried once, and 615 MiB of headroom may not survive a prompt that actually reaches 8k tokens on both slots; the peak VRAM of `-c 8192 --np 2` was not logged, only the engine's 14 634 MiB plan estimate; the end-to-end column carries a 33-token prefill and connection setup, so it understates what a long generation would see.
