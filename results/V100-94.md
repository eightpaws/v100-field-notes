# V100-94 - Images on 4060 Ti, code on V100

_Measured on an NVIDIA GeForce RTX 4060 Ti 16 GB (sm_89) under Windows 11, driver 617.14, with the same card driving the display. Baseline re-used from V100-73 (Tesla V100-SXM2 16 GB, sm_70, driver 580)._

**Question.** The image factory held a V100 for six hours and consumed five consecutive queue ticks. On the 4060 Ti (Ada, 16 GB, SDXL-turbo) generation should run comparably fast, leaving the V100 free for code. This is not model acceleration but idle removal - the cheapest win available.

**Environment.**
| Item | Value |
|---|---|
| GPU | RTX 4060 Ti 16 GB, sm_89, 16 380 MiB, driver 617.14 |
| Host | Windows 11, desktop compositor holding ~1.6 GB of VRAM |
| Runtime | torch 2.11.0+cu128, diffusers 0.43.0, cuDNN 91900 |
| Pipeline | `StableDiffusionXLPipeline.from_single_file`, fp16, VAE `force_upcast=False`, VAE slicing + tiling |
| Checkpoint | `DreamShaperXL_Turbo_v2_1.safetensors`, 6 939 220 250 B (identical file used in V100-73) |
| Sampling | guidance 0.0, 12 product-photo prompts, one image per prompt |

**Commands.**
```
/d/venvs/image/Scripts/python.exe D:/Programs/hermes/cache/scratch/v94_pc.py
```
The driver script loads the pipeline once, generates a 512 px / 2-step warm-up image, then runs three consecutive repeats of 12 images for each mode (1024x1024 at 30 steps, 768x768 at 30 steps, 1024x1024 at 6 steps) and records per-image wall time, peak `nvidia-smi` memory and `torch.cuda.max_memory_reserved`.

**Results.**

| Mode | 4060 Ti, s/image | 4060 Ti, images/h | V100 (imgd), s/image | V100, images/h | PC vs V100 |
|---|---|---|---|---|---|
| 1024x1024, 30 steps | 6.93 ± 0.18 | 519 | 5.06 | 711 | 37 % slower |
| 768x768, 30 steps | 4.40 | 818 | 3.41 | 1056 | 29 % slower |
| 1024x1024, 6 steps | 1.91 ± 0.02 | 1885 | 1.78 | 2020 | 7 % slower |

Peak VRAM (`nvidia-smi`, includes the desktop): 13 440 MiB at 1024/30 and 15 947 MiB at 1024/6 out of 16 384 MiB. Pipeline load from warm page cache: 4.9 s.

The card's acceptance threshold was "at least 1500 images per hour on the PC". It is met only at the 6-step turbo preset (1885/h), and only because the V100 number at the same preset is slightly higher (2020/h). At the 30-step preset that quality work actually needs, the PC delivers 519 images per hour against 711 on the V100.

**Repeats.** n = 3 repeats of 12 images per mode, mean ± stdev across repeats. 1024/30: 6.79, 6.88, 7.13 s (6.93 ± 0.18). 1024/6: 1.89, 1.92, 1.92 s (1.91 ± 0.02). 768/30: 10.01, 4.41, 4.39 s - the first repeat carries a 16.0 s outlier on the first image after the resolution switch (allocator churn, that repeat's minimum is 4.12 s), so the steady-state 4.40 s from the two clean repeats is reported.

**Verdict.** Mixed: the 4060 Ti reaches 1885 images per hour on the turbo preset and 519 at 30 steps, but it is slower than the V100 in all three modes, so moving the factory would not speed generation up. Its real value is different - it produces 519-1885 images per hour without occupying the V100, which is what the queue lost six hours of code time to.

**Result type.** Mixed.

**Does not show.** The two sets of numbers come from different code paths: V100-73 was measured through the `imgd` HTTP service on torch 2.10, this run through a diffusers pipeline on torch 2.11, so part of the gap is server-versus-pipeline overhead rather than silicon. Prompt sets are the same style and length but not the same strings. Image quality was not compared (same checkpoint and step counts, but cuDNN is active here and disabled on sm_70, which changes convolution paths). Upscaling was not measured on the PC at all. The VRAM peak on Windows includes the desktop compositor; a headless Linux host would show a lower number, and 15 947 of 16 384 MiB means no second service fits next to 1024 px generation.
