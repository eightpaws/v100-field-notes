# V100-15 — Stack snapshot: how long sm_70 stays supportable

_Recorded on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Positive.

**Question.** CUDA 13 dropped Volta from offline compilation and PyTorch 2.15 removes the cu126 builds — the last
ones that ship sm_70 binaries. That is a closing window: after it, keeping this card working means building
everything from source against CUDA 12.6. Can the working stack be frozen while it is still reproducible?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB / 580.178.04 / 7.0 (sm_70) |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |
| Environments frozen | video (302 packages) · vLLM (191 packages) |
| Storage | `/srv/media/ai-cache/wheels` on the HDD pool, 4.7 TB free |

**Commands** (verbatim):

```bash
# freeze both environments
/srv/media/ai-cache/venv-video/bin/pip freeze  > /srv/media/ai-cache/wheels/requirements-video.txt
/home/hermes/venvs/vllm/bin/pip     freeze  > /srv/media/ai-cache/wheels/requirements-vllm.txt

# pull the critical wheels so a restore does not need the network
pip download --no-deps -d /srv/media/ai-cache/wheels \
  torch==2.10.0 torchvision==0.25.0 transformers==4.57.6 diffusers==0.39.0 \
  accelerate==1.16.0 safetensors==0.8.0 numpy==2.3.5
```

**Results.**

| Item | Value |
|---|---|
| Frozen requirement sets | `requirements-video.txt` (302 packages), `requirements-vllm.txt` (191 packages) |
| Wheels kept on disk | 12 wheels, 2.3 GB |
| Disk left | 4.7 TB free |

Why this was urgent rather than tidy: the stack changed twice in one day on its own. First the video venv ended up
with torch 2.14.0+cu130 — no sm_70 kernels at all. Then a background job rolled it back to 2.5.1+cu121, where cuDNN
finds no engine for fp16 convolutions. Both times the render factory silently produced zero frames instead of
failing loudly. Every recovery took half an hour of guesswork.

**Repeats.** Snapshot taken once. The stack mutated twice within 24 hours, so the useful cadence is "re-verify after
any update", not "verify once".

**Verdict.** Freeze the stack and keep the wheels on disk — the failure mode here is silent, and after CUDA 13 / PyTorch
2.15 the only way back is a source build. Rule for this card: update nothing on a V100 without a reason you can write
down. One item is still open and is stated here rather than hidden: the offline restore test on a clean VM (music,
video and TTS pipelines on the pinned versions) has not been run, so the snapshot is complete but unproven end to end.

**Does not show.** Does not show that the snapshot restores: the offline clean-VM test is still not run, so the wheels are complete but unproven end to end. Package counts are `pip freeze` at snapshot time; nothing here verifies the pinned set still drives the three pipelines.

**Follow-up.** Queued as V100-64 (offline restore of the snapshot on a clean VM). The results will be published here and this card updated when that run lands — the caveat above is tracked work, not a permanent excuse.
