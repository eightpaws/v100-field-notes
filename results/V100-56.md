# V100-56 - 32k with q8_0 KV and 64k with q4_0 KV on a 7B model

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** The parent card (V100-02) reported that 32k "loaded but was never measured" and that 64k failed with OOM at q8_0 KV. Does q4_0 KV, which is half the size, carry 64k context on this card, and what does either setting cost in prefill and decode speed?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine | llama.cpp b1b770d (1.0.0-dev, build 1), CUDA backend, built with GCC 12.4.0 |
| Model | qwen2.5-coder-7b-instruct-q4_k_m.gguf, 4.68 GB, Q4_K - Medium, 7.62 B params |
| Host | Proxmox VE VM: 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04 |
| Flags | `-ngl 99 -fa on`, KV type varied per configuration, `-r 3` |
| Harness | `llama-bench` from the same build, no server in the loop |

**Commands.** Run through the queue runner, which takes the GPU lease and clears the card first:

```bash
/root/bin/v100-run.sh V100-56 -- /root/bin/v56_bench.sh
```

The script ran two configurations, three repetitions each:

```bash
llama-bench -m /srv/media/ai-cache/downloads/qwen2.5-coder-7b-instruct-q4_k_m.gguf \
  -ngl 99 -fa on -p 32768 -n 128 -ctk q8_0 -ctv q8_0 -r 3 -o json

llama-bench -m /srv/media/ai-cache/downloads/qwen2.5-coder-7b-instruct-q4_k_m.gguf \
  -ngl 99 -fa on -p 65536 -n 128 -ctk q4_0 -ctv q4_0 -r 3 -o json
```

VRAM was sampled from `nvidia-smi --query-gpu=memory.used` every 0.5 s while each configuration ran; the maximum is reported below.

**Results.**

| Context | KV | Prefill tok/s | Decode tok/s | VRAM peak |
|---|---|---|---|---|
| 32 768 | q8_0 | 1844.3 +/- 0.3 | 126.0 +/- 0.2 | 5995 MiB |
| 65 536 | q4_0 | 1236.3 +/- 0.1 | 125.7 +/- 0.2 | 6083 MiB |

**Repeats.** `n=3` per configuration, mean +/- sample standard deviation from `llama-bench`. The deviations are tiny because each repetition runs the same shape on an idle card; the spread does not cover session-to-session variation.

**Baseline.** The earlier single run of this card on an older build (commit af5c583) gave 1860 tok/s prefill and 121.5 tok/s decode at 32k/q8_0, and 1247 / 121.8 at 64k/q4_0. Prefill reproduces within 1 %, decode comes out 3.5 % higher on the current build.

**Verdict.** Both settings work: 32k with q8_0 and 64k with q4_0 KV fit on one 16 GB card, and decode stays at 126 tok/s at either context length. Compressed KV is what makes 64k possible at all; the price is prefill, which drops by a third from 32k to 64k.

**Does not show.** Measured on a 7B model, not on the 14B the parent card is about - a 14B model needs roughly twice the KV bytes per token, so this does not prove 64k fits at 14B. No retrieval or needle test was run, so the numbers say the context loads and keeps its speed, not that answer quality survives 4-bit KV. Single session, one build.

**Result type.** Positive.
