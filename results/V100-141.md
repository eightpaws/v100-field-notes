# V100-141 — cuDNN 8 environment for graphics and video models

**Question.** cuDNN 9 shipped with PyTorch 2.10 has no fp16 convolution kernels for compute capability 7.0, so on the V100 Real-ESRGAN, SDXL inpainting and CogVideoX fail with `RuntimeError: GET was unable to find an engine to execute this computation`. Does a separate environment pinned to PyTorch 2.3.1 + cuDNN 8.9 run the same three scripts without disabling cuDNN?

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, sm_70, 900 GB/s, 16 GB |
| Driver | 580 (last branch that still carries sm_70) |
| New venv | `/home/hermes/venvs/cu121` — Python 3.12, torch 2.3.1+cu121, torchvision 0.18.1, cuDNN 8.9.2.26 |
| Baseline venv | `/var/lib/ollama/venvs/video` — torch 2.10.0+cu128, cuDNN 9 |
| Host | Proxmox VM on EPYC 7282, Ubuntu 24.04, guest 24 vCPU |

**Commands.** The driver scripts survived, the launch strings did not, so the exact command lines are not reproduced here (they are not reconstructed from memory on purpose):

- video: `/srv/media/projects/video-720/video720.py`, run at 480x320, 17 frames, 20 steps;
- background inpaint: `/srv/media/projects/depth-bg/bg_inpaint.py`, 3 product photos;
- ESRGAN: result written to `/srv/media/projects/upscale-bench/result.json`, 6 product photos.

Interpreter for all three: `/home/hermes/venvs/cu121/bin/python`.

**Results.**

| Task | What was run | Time | Peak VRAM | Quality signal |
|---|---|---|---|---|
| Real-ESRGAN x4 | 6 product photos | 0.775 s per image (0.75–0.9) | 2 445 MiB | PSNR 33.5 dB, SSIM 0.942, sharpness 18.3 vs 12.0 in the original (lanczos: 6.4) |
| SDXL inpainting | 3 product photos, background replacement | 18.5 s total | 5 295 MiB | product SSIM 0.838, background changed on 76.9 % of pixels |
| CogVideoX | 480x320, 17 frames, 20 steps | 46 s generation, 2.7 s per frame, 7 s model load | 11 119 MiB | median sharpness 272.2, median motion 10.8, 0 stuck frames |
| CogVideoX at 720p | same script, higher resolution | failed | — | `CUDA out of memory. Tried to allocate 1.32 GiB` |

On the baseline stack (torch 2.10 + cuDNN 9) the ESRGAN and video runs abort with `GET was unable to find an engine to execute this computation`; SDXL inpainting only worked there with `torch.backends.cudnn.enabled = False` plus CPU offload.

**Repeats.** Single run per task; ESRGAN processed 6 images in one pass, spread 0.75–0.9 s per image.

**Verdict.** Positive: cuDNN 8 restores the missing convolution path on sm_70, and all three pipelines run with cuDNN enabled. It removes the engine failure, not the memory ceiling — 720p video still runs out of VRAM after the model has loaded.

**Result type.** Positive.

**Does not show.** Fidelity metrics favour lanczos over ESRGAN (33.5 vs 39.4 dB PSNR), so the sharpness gain is not automatically a quality gain, and no frames were inspected by eye. Video was measured only at 480x320 with 17 frames; the 720p failure is a VRAM limit and says nothing about whether a tiled VAE would fit. Launch strings were not archived, so a reader cannot reproduce the exact flags from this card.
