# V100-58 - Throughput, batching, quality

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04, Ubuntu 24.04.5._

**Question.** Does the fork beat llama.cpp on total throughput once 4 to 8 clients ask at the same time, and by how much? Success metric: aggregate tokens per second at 1, 4 and 8 concurrent clients, with the same model and 128 output tokens per request.

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute capability 7.0, 16384 MiB |
| Driver / CUDA | 580.178.04 / 12.9 |
| Engine | 1Cat-vLLM 1.5.4, GGUF backend |
| Model | qwen2.5-coder-7b-instruct, Q4_K_M GGUF |
| Server flags | `--quantization gguf --max-model-len 4096 --gpu-memory-utilization 0.6` |
| KV cache | runtime default `int8_per_token_head`, 3.70 GiB, 134 368 tokens, 8398 blocks |
| Model load | 5.07 GiB in 22.3 s |

**Commands.** The driver script was not preserved. The launch line is reconstructed from the `non-default args` record of the server log (`utils.py:278`), not from memory:

```
vllm serve /srv/media/ai-cache/downloads/qwen2.5-coder-7b-instruct-q4_k_m.gguf \
  --tokenizer /srv/media/ai-cache/downloads/qwen25c7b-awq \
  --quantization gguf --max-model-len 4096 --gpu-memory-utilization 0.6 \
  --host 127.0.0.1 --port 18420
```

Client side: chat completions against `http://127.0.0.1:18420/v1`, 128 output tokens per request, three requests per single-stream batch, then one 4-client and one 8-client wave of 128 tokens each. The client harness itself was not preserved.

**Results.**

| Mode | Tokens | Run A | Run B |
|---|---|---|---|
| Single request, tok/s | 128 | 109.4 / 114.5 / 115.5 | 110.2 / 112.2 / 115.3 |
| 4 parallel, aggregate tok/s | 512 | 403.2 | 168.6 |
| 8 parallel, aggregate tok/s | 1024 | 702.2 | 714.8 |
| Server start, s | - | 105.1 | 120.1 |

**Artifacts.** `/srv/media/night/v100_58.json` (run A, 238 B), `/srv/media/night/v100_58_run.log` (run B, 239 B), `/srv/media/night/v100_58_server.log` (117 KB: flags, KV cache, load time).

**Repeats.** n=2, two runs on two separate server starts. Eight clients: 702.2 and 714.8 tok/s, 1.8 percent apart, inside the noise of a run-to-run comparison. Single stream: three requests per run, spread 109.4-115.5 tok/s. Four clients disagree by 2.4x between runs and the cause cannot be recovered from the artifacts.

**Result.** Two runs, both taken with the same server flags on the same card. Eight concurrent clients produce 702.2 and 714.8 aggregate tok/s, so the batching gain is real and repeatable. A single stream reaches 109-116 tok/s, which is slower than llama.cpp on the same 7B model (132 tok/s measured earlier in this series). Server start costs 105-120 s against 3-4 s for llama.cpp. The 4-client figure is the weak point: 403.2 in run A and 168.6 in run B. The earlier note attributed the low figure to identical prompts and prefix-cache reuse, but no artifact ties a given run file to a prompt mode, so 4 clients are quoted as a lower bound and only 8 clients are quoted as stable.

**Verdict.** The fork's batching is real and repeatable at eight clients (about 710 tok/s), but a single stream is slower than llama.cpp and start-up is thirty times longer, so the win belongs to a task queue, not to interactive editing.

**Result type.** Mixed.

**Does not show.** Answer quality on 30 questions was never run, although the acceptance criterion demanded it. No two-hour stability test. TTFT p50 and p95 were not recorded. The 4-client regime is unstable between runs and its cause is not established. The default int8 KV cache was not compared against fp16. The attribution of identical versus unique prompts to the two run files was lost, so the prefix-cache explanation stays a hypothesis.

**Follow-up.** Not yet queued as a card: the 4-client case needs three repeats with unique prompts per client before the number can be quoted; until then read it as a lower bound.
