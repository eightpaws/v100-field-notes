# V100-65 - Batch size does not change prefill at 8k or 16k

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU (EPYC 7282), 94 GiB RAM, driver 580.178.04, Ubuntu 24.04._

**Question.** A parent card (V100-10) concluded that `num_batch` 2048 is the best prefill setting on this card, but its numbers covered 1k and 16 440 tokens only, they came from Ollama, and the value for 4096 was never recorded. Does the optimum move at 8k, and does 4096 help or run out of memory at 16k?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16144 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine | llama.cpp build 51831d47 (1224), CUDA backend, CUDA toolkit 12.9, GCC 12 |
| Model | deepseek-coder-v2-lite Q4_K_M, 9.65 GiB, 15.71 B parameters, fully on the card |
| Host | Proxmox VE VM: 24 vCPU, 94 GiB RAM, Ubuntu 24.04 |
| Flags | `-ngl 99`, `n_batch` swept 512 / 1024 / 2048 / 4096, `-r 3` |
| Harness | `llama-bench` from the same build, no server in the loop |

**Commands.** Run through the queue runner, which takes the GPU lease and clears the card first:

```bash
/root/bin/v100-run.sh V100-65 -- /root/llama-old/build/bin/llama-bench \
  -m /srv/media/ai-cache/downloads/deepseek-coder-v2-lite-q4_k_m.gguf \
  -p 8192 -b 512,1024,2048,4096 -r 3 -ngl 99

/root/bin/v100-run.sh V100-65b -- /root/llama-old/build/bin/llama-bench \
  -m /srv/media/ai-cache/downloads/deepseek-coder-v2-lite-q4_k_m.gguf \
  -p 16384 -b 512,1024,2048,4096 -r 3 -ngl 99
```

One model load per command: `llama-bench` sweeps every `-b` value inside a single process, so the card was loaded twice in total, not eight times.

**Results.** Prefill tok/s at 8k and 16k prompt length:

| Prompt tokens | b=512 | b=1024 | b=2048 | b=4096 |
|---|---|---|---|---|
| 8192 | 2648.97 +/- 3.18 | 2649.09 +/- 2.43 | 2649.85 +/- 2.37 | 2651.48 +/- 1.66 |
| 16384 | 1898.13 +/- 0.97 | 1898.16 +/- 0.50 | 1897.60 +/- 1.44 | 1897.36 +/- 0.35 |

Decode at `tg128` came out at 172.6 - 173.2 tok/s in every configuration. VRAM peak at 16k with b=2048 was 15 385 MiB of 16 144, sampled at 1 Hz during a single run, so 4096 does not run out of memory either.

**Repeats.** `n=3` per configuration, mean +/- sample standard deviation printed by `llama-bench`. The spread inside one configuration (up to 3.2 tok/s) is larger than the difference between the extreme batch sizes (2.5 tok/s at 8k), which is why the honest reading is "no effect" rather than "4096 is 0.1 % faster".

**Baseline.** The parent card recorded 2713 tok/s at 8k and 1976 tok/s at 16k, single run, on a different build. This build is 2 % and 4 % lower at the same lengths, so the gap between builds is larger than anything batch size does. The Ollama figure that started this follow-up (1776 tok/s at `num_batch` 2048 against 1351 at the default 512) stands for Ollama; it does not transfer to llama.cpp, where the prefill path already batches internally.

**Verdict.** On this card, in llama.cpp, `n_batch` between 512 and 4096 changes nothing measurable at 8k or 16k: prefill sits at 2649 tok/s at 8k and 1898 tok/s at 16k across the whole range, and 4096 is safe (peak 15.4 GiB). Keep the default; the "hold 2048" rule belongs to Ollama.

**Does not show.** It does not re-measure Ollama's own `num_batch` path on a 14B model, which is where the original claim came from - that half of the parent card is untouched. Prompt length was set by `-p`, not verified against `prompt_eval_count` of a real request. The earlier out-of-memory on 30B-A3B with `-ncmoe 8` at 8k was not reproduced in this series. One model, one build, one card; nothing here says how batch size behaves on a card with more VRAM, where the compute buffers have more room.

**Result type.** Negative.
