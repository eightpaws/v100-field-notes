# V100-12 — 1Cat-vLLM: a modern serving stack that still builds for sm_70

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Mixed.

**Question.** Upstream vLLM has effectively left Volta behind, and Ollama's GGUF path is a dead end for anyone who
wants an OpenAI-compatible serving stack with real batching. `1Cat-LLM` is a vLLM fork that keeps SM70 kernels
(AWQ W4A16, TurboMind, FlashAttention-V100, FP8 KV storage). Does it actually start and serve on a single 16 GB
card — and what does it cost against plain llama.cpp?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Stack | 1Cat-vLLM 1.5.4 (fork of vLLM), wheel `cp312/cu128`, own venv `/home/hermes/venvs/vllm` |
| Dependencies pulled in | fastapi 0.141, uvicorn 0.54, flashinfer 0.6.11 |
| Model | qwen2.5-7b-instruct, GGUF |
| Baseline | llama.cpp (sm_70 build) and Ollama on the same model |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |

**Commands** (verbatim launch line, recovered from the run log `v100_12_test.log`; an earlier version of this card said the flag list was lost, which was wrong):

```bash
/home/hermes/venvs/vllm/bin/python -m vllm.entrypoints.openai.api_server \
  --model /models/qwen2.5-7b-instruct.gguf \
  --tokenizer /models/qwen2.5-7b-instruct.gguf \
  --quantization gguf --dtype half --max-model-len 4096 \
  --gpu-memory-utilization 0.75 --port 8091 --host 127.0.0.1 --enforce-eager
```

Two client calls through the OpenAI-compatible endpoint: a short one (44 tokens) and a long one (300 tokens).

**Results.**

| Measurement | Value |
|---|---|
| Server start | 90.2 s |
| Short request | 44 tokens in 6.2 s (7.1 tok/s — dominated by time to first token) |
| Long request | 300 tokens in 10.5 s (28.7 tok/s) |
| llama.cpp, same card, 7B | 38–40 tok/s |
| Ollama Q4, earlier reference | 62–66 tok/s |

**Repeats.** Single run, two requests. One request pair is enough to show the stack works; it is not enough to
publish a throughput figure, so treat 28.7 tok/s as an order of magnitude.

**Verdict.** The fork runs: a real modern serving stack on Volta, roughly a quarter behind llama.cpp on 7B GGUF, with
an OpenAI API and batching model that llama.cpp does not give you. Two pitfalls cost the most time — `--disable-log-requests`
is gone in this fork (use `--enforce-eager`), and the card must be empty first: Ollama holding 10.5 GB through
llama-server makes the engine refuse to start. Note that the fork's headline numbers (892 tok/s) come from 4×V100-32GB
with NVLink; nothing about multi-GPU recipes transfers to one 16 GB card.

**Does not show.** Does not show throughput: two requests (44 and 300 tokens) cannot support a tok/s figure, and the batching the fork exists for was never exercised. VRAM, multi-hour stability and answer quality were not measured although the plan asked for them. The 892 tok/s headline comes from 4×V100-32GB with NVLink and is neither reproduced nor comparable to one 16 GB card.

**Follow-up.** Queued as V100-58 (batching at 1/4/8 clients, aggregate throughput, answer quality). The results will be published here and this card updated when that run lands — the caveat above is tracked work, not a permanent excuse.
