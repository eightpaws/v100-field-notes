# V100-43 — llama-server as a working server: prefix cache and batch

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-11 showed: prefix cache in llama.cpp for 6k gives 186 ms against 1541 (×8), and tail fix - 95 ms; V100-16 gave +7.4% decode compared to Ollama. Therefore, the working setup (agent, LibreChat, packages) should be on llama-server with `--cache-reuse`, not on Ollama.

**Result.** llama-server as a working server has been verified: prefix cache actually saves time. llama.cpp master 51831d4, CUDA 12.9, Qwen2.5-Coder-7B Q4_K_M (entirely on GPU), flags `-b 2048 -ub 512 -fa 0 -ctk f16 -ctv f16 --cache-reuse 256 -np 2 --jinja`, context 8192. The same system prompt of 2067 tokens, three consecutive questions: | Request | Total | Tokens in prompt | Prefill | Decode | |---|---|---|---|---| | 1 (cold) | 1.18 s | 2067 | 845 ms | 105 tok/s | | 2 | 0.39 s | **9** | 89 ms | 107 tok/s | | 3 | 0.39 s | **11** | 90 ms | 107 tok/s | Cache cuts prompt parsing from 845 to 89 ms (9.5 times), the round takes 0.39 s instead of 1.18. For an agent sending the same system prompt in each request, this is the main win - as promised by V100-11. The rake I hit after three attempts: **quantized KV (`-ctk q8_0 -ctv q8_0`) does not load with `-fa 0`** - context is not created at all, there's a general and vague error. Compressed KV works only with FA enabled; for Qwen3-Coder FA drops speed, so the choice is either fp16-KV without FA or q8_0-KV with FA. For Qwen2.5-Coder-7B, FA does not interfere. Second: the server on Qwen3-Coder with `-c 8192` and `-ncmoe 8` does not start - there's not enough VRAM for 4 slots plus compute buffer; it needs ncmoe of at least 16 or context 4096.
