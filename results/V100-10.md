# V100-10 — Prefill and batching: where a V100 actually loses throughput

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Positive.

**Question.** The same V100 reported 360–703 tok/s of prefill in one test suite and ~1708 tok/s in a
side-by-side against a desktop card. If the hardware is identical in both, the 5x spread has to come from
defaults — batch size, context length, missing FlashAttention — and not from the V100. Which handle moves it?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine | Ollama 0.40.16, FlashAttention on, q8_0 KV |
| Model | qwen2.5-14b-instruct, Q4 GGUF |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |
| Variable | `options.num_batch` = 128 / 512 / 2048 / 4096 |

**Commands** (request shape as issued; the driver script was not preserved). One request per batch size, prompts
of ~1k, 8k, 16k and 16 440 tokens:

```bash
curl -s http://127.0.0.1:11434/api/generate -d '{
  "model": "qwen2.5-14b-instruct",
  "prompt": "<prompt of the target length>",
  "stream": false,
  "options": {"num_ctx": 32768, "num_batch": 2048, "num_predict": 8, "temperature": 0}
}'
```

Prefill throughput is read from `prompt_eval_duration` in the response, not from wall time.

**Results.**

| num_batch | prefill tok/s | prompt length |
|---|---|---|
| 128 | 587 | ~1k |
| 512 (Ollama default) | 1351 | ~1k |
| 2048 | 1776 | ~1k |
| 2048 | 1441 | 16 440 tokens |

1k, 8k and 16k prompts all peak at `num_batch=2048`; `4096` was issued but produced no better point and is not
in the table.

**Repeats.** Single run per point, `n=1`; no error bars measured.

**Verdict.** Set `num_batch=2048` explicitly on a V100 — it is ×3 over 128 and +31 % over the Ollama default, and
the default is the main reason the card looks slow in off-the-shelf setups. The penalty for long prompts is real
but small: −19 % at 16 440 tokens.

**Does not show.** Does not show a comparison against a desktop card: there is no second GPU in this run, so the original 1708-vs-1726 claim is not reproduced here — only the V100 side is measured. The 8k and 16k points are asserted from the run log, and only the 1k and 16 440-token numbers were kept. `num_batch=4096` was issued; its result was not recorded.

**Follow-up.** Queued as V100-65 (prefill at 8k and 16k, plus num_batch=4096) — this card is updated when that run lands, not left as a caveat.

**Raw.** `raw/runs/` has no file for this card — the numbers survived only in the run log, the log was not kept.
