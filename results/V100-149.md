# V100-149 — llama-server throughput with ten concurrent clients

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-43 showed that the prefix cache pays for itself when one client keeps sending the same system prompt. With ten simultaneous clients that each bring a different 1400-token prefix, does the cache still hit, and does the card serve more than one stream at a time — or must an agent loop be built as one slot per role?

**Environment.**

| Component | Value |
|---|---|
| GPU | Tesla V100-SXM2 16 GB, compute capability 7.0 |
| Driver | 580.178.04, CUDA toolkit 12.9 (installed without root, home directory) |
| Engine | llama.cpp 1.1.0-dev, commit 28148b5, `llama-server` |
| Model | qwen2.5-7b-instruct Q4_K_M, 5.1 GB on disk, `-ngl 99` (whole model on the card) |
| Host | Ubuntu 24.04, 24 vCPU, 94 GiB RAM |
| Server flags | `--cache-reuse 256 --metrics`; host prompt cache left at its default `--cache-ram 8192` MiB |
| Workload | 10 clients, prefix 1400 token ids each (disjoint vocabularies), 24 generated tokens, no thinking |

**Commands.**

```bash
bash /root/bin/v100-run.sh V100-149 -- bash /root/v149_driver.sh
```

Inside the driver, one server start per configuration:

```bash
/home/hermes/llama-master/build/bin/llama-server -m /models/qwen2.5-7b-instruct.gguf \
  -ngl 99 -c 8192 -np 2 --cache-reuse 256 --port 18452 --host 127.0.0.1 --metrics
NP=2 CTX=8192 REPS=3 python3 /root/v149_harness.py
```

The harness posts ten streaming `/completion` requests at once (a `threading.Barrier` releases them together), prompt as token ids, `n_predict 24`, `cache_prompt true`, and records the client-side time to the first streamed token. Configurations: `-np 1 -c 4096`, `-np 2 -c 8192`, `-np 4 -c 16384`, three waves each.

**Result.**

| Configuration | TTFT median | TTFT max | Burst throughput | Decode per client | VRAM |
|---|---|---|---|---|---|
| 1 client, `-np 1`, 4096 | 491 ± 6 ms | 510 ms | 111 tok/s | 111 tok/s | 5557 MiB |
| 10 clients, `-np 1`, 4096 | 1565 ms (3.19×) | 3022 ms | 74 tok/s | 111 tok/s | 5557 MiB |
| 10 clients, `-np 2`, 8192, cold | 3202 ms (6.52×) | 5922 ms | 39 tok/s | 32 tok/s | 5781 MiB |
| 10 clients, `-np 2`, 8192, warm | 1130 ms (2.30×) | 2045 ms | 104 tok/s | 52 tok/s | 5781 MiB |
| 10 clients, `-np 4`, 16384, cold | 3092 ms (6.29×) | 5714 ms | 40 tok/s | 32 tok/s | 6229 MiB |
| 10 clients, `-np 4`, 16384, warm | 1077 ms (2.19×) | 1713 ms | 122-124 tok/s | 66 tok/s | 6229 MiB |

Ratios are against the single-client TTFT of 491 ms. Cold means the first wave after the server start, warm means repeats 2-3 of the same ten prefixes; warm medians are stable within 3 ms at `-np 2` and 27 ms at `-np 4`.

**Verdict.** Mixed: the cache does not collapse under ten different prompts — on the second pass every client is served with `prompt_n = 1` — but extra slots do not make the card faster: total throughput moves from 111 to 104-124 tok/s (+7-12 %) while decode per client falls from 111 to 52-66 tok/s, and the first burst after a server start costs 6.3-6.5× the single-client TTFT.

**Result type.** Mixed.

**Does not show.** Answers are 24 tokens with no tool calling and no growing context inside a dialogue; `--cache-ram` was left at 8192 MiB, so prefixes longer than roughly 2k and eviction under host memory pressure are not covered; decode per client is taken from the server's own `eval time` lines, not from client-side timestamps; the 10-client load is a single burst, not a sustained arrival process.
