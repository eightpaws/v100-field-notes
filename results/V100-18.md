# V100-18 — xllama.cpp: compress KV instead of q8

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Fork of llama.cpp with TurboQuant/PlanarQuant/IsoQuant (compression of each record) and TriAttention (eviction of low-value records). Claimed 20–37× KV cache compression when used together—this translates our context ceiling from "8–16k" to "hundreds of thousands," if quality holds.

**Environment.** Tesla V100-SXM2-16GB (sm_70), driver 580, CUDA 12.9, guest VM on home Proxmox; engine: not detected in artifacts; model: qwen2.5-coder-14b.gguf

**Result.** Compressed KV in xllama.cpp works, but on long context it becomes too slow. Built with xllama.cpp f9287a9 (fork of llama.cpp from April 2026 with TurboQuant/PlanarQuant/IsoQuant/TriAttention), CUDA 12.9.41, model Qwen2.5-Coder-14B Q4_K_M, `-ngl 99 -fa 1`, one slot. First short tests (pp256/tg64): | KV Type | prefill | decode | |---|---|---| | f16 | 1183 | 68.1 | | turbo3 | 1098 | 51.3 | | planar3 | 894 | 47.5 | | iso3 | 654 | 44.1 | On short prompts, compression costs 20-45% in speed. Further - the main issue visible only on real long prompt (12k tokens): | Configuration | VRAM | prefill | decode | |---|---|---|---| | f16, 32k | 15.3 GB | **8446 ms** (1426 tok/s) | 52.0 | | planar3, 64k | 11.6 GB | **63936 ms** (188 tok/s) | 33.9 | That is, planar3 saves 3.7 GB and allows to raise context from 32k to 64k, but prompt parsing becomes **7.6 times slower** - a minute for 12k tokens against 8.4 seconds. For document search and RAG this makes the configuration unusable: prefill on 60k tokens will take minutes. Additionally: f16 on 64k does not start at all (segfault on load), so "64k on 16 GB" is possible only with compressed KV - but the cost is paid in minutes of waiting. Quality: model did not respond meaningfully on 12k prompt ("?????????"), while it was trained on 32k, and the server itself warned `n_ctx_seq (65536) > n_ctx_train (32768)`. Without RoPE scaling going beyond 32k is impossible. Conclusion: rejected in current form. The idea of compressed KV is correct for memory, but on V100 dequantization in tensor cores eats up all the gain on prefill. Worth rechecking when Hadamard rotation of KV arrives upstream in llama.cpp (PR #21038 and kernels #23615) - there dequant is built into matmul, not a separate pass. Artifacts: `/srv/media/night/v100_18_server.log` (planar3), `/srv/media/night/v100_18_f16.log` (f16 32k).


**Verdict.** Compressed KV in xllama.cpp works, but on long context it becomes too slow.
