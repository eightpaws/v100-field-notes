# V100-116 — What a generated project still needs before delivery

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** When a 7B coder is asked for a whole small project in one shot, how much of the result is actually deliverable to a paying client — and what is missing?

**Environment.** llama.cpp 1.0.0-dev build129 (commit af5c583, CUDA 12.9), Qwen2.5-Coder-7B-Instruct-Q8_0 (8.1 GB); Tesla V100-SXM2-16GB, driver 580.178.04; Proxmox VM, 24 vCPU, 94 GiB RAM; Python 3.12; one `llama-server -ngl 99 -c 8192 --jinja -np 1`, temperature 0, `max_tokens` 5500; peak VRAM 8269 MiB during generation.

**Commands.**

```
/root/bin/v100-run.sh V100-116 -- python3 /root/v116_deliver.py
```

Inside the driver, one server per run:

```
llama-server -m /srv/media/ai-cache/downloads/qwen7b-quants/qwen2.5-coder-7b-instruct-q8_0.gguf \
  --port 18371 -ngl 99 -c 8192 --jinja --host 127.0.0.1 -np 1
```

Three prompts, each asking for a complete small project as files in `=== FILE: path ===` blocks: (1) FastAPI service with JWT auth and PostgreSQL, tests, Dockerfile, docker-compose; (2) CLI ETL tool moving CSV into SQLite with argparse and env-based config; (3) REST API client with token from the environment, retry on 429/5xx, JSONL output and mocked HTTP tests. The scoring script is plain Python (`ast.parse`, regex checks) — no ruff, mypy, gitleaks or trufflehog were involved in this run.

**Repeats.** Single run per prompt; three different prompts instead of repeating one (n=3 projects, temperature 0, where a repeat returns the same text). Total wall time 63.7 s.

**Result.**

| Project | Files | Score | Failed checks |
|---|---|---|---|
| FastAPI + JWT + Postgres | 12 | **10/10** | none |
| CLI ETL into SQLite | 8 | 8/10 | LICENSE, Dockerfile |
| REST API client | 7 | 8/10 | Dockerfile, secret scan (test constant) |

Checklist of ten items: README with run commands, LICENSE file, env sample when the code reads environment variables, pinned requirements, no hardcoded credentials, tests present, `.gitignore` covering the env file, Dockerfile, sane file names, code parses with no stub markers.

Mean 8.67/10, best 10/10 against a card criterion of 8/10. The only scanner hit is `TOKEN = 'test_access_token'` inside the API-client test file: a fixture placeholder, not a key. Generation: 3267, 966 and 853 completion tokens at 82–84 tok/s, longest response 39.6 s, whole run 63.7 s including 2 s server start.

**Verdict.** Deliverable, but only what was asked for: the model emitted a Dockerfile and a LICENSE exactly where the prompt named them and skipped them where it did not. The delivery checklist therefore belongs in the prompt, not in expectations — with the full checklist stated, one of three projects came out client-ready without edits.

**Result type.** Mixed.

**Does not show.**

- Secret detection was a regex scan (AWS key shape, private-key header, `sk-`/`ghp_` prefixes, literal credential assignments, placeholder names excluded), not gitleaks or trufflehog; git history was not scanned because the projects are single-shot outputs, not repositories.
- Projects were never built or run: `docker compose up`, `pytest` and container builds were not executed. The score is static (files present, imports parse, no stub markers), not functional.
- The checklist is our own ten items; a stricter list (typed code, coverage, CI workflow) would lower the score.
- A first run with `max_tokens` 3000 was truncated on the 12-file project (7.67/10 mean); the published numbers are the second run at 5500.
- The harness strips markdown code fences the model wraps around each file. Without that step every generated file fails to parse at line 1 — the model's raw output is not copy-paste clean.
