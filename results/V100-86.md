# V100-86 — v100-llm-kit: prebuilt SM70 binaries vs our own build

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** `andrewleech/v100-llm-kit` ships binaries compiled only for sm_70 plus serve scripts, with no source patches of its own. The card asks one thing: on the same GGUF and the same flags, does the shipped `ik_llama.cpp` build beat the `llama.cpp` build we compile locally, and does it start under our driver at all?

**Environment.** GPU Tesla V100-SXM2 16 GB (sm_70), driver 580; kit: `ik_llama.cpp` build 4578, commit 022bd00a, archive `ik_llama.cpp-qwen3-linux-sm70.zip` (608 MB, CUDA runtime and cuBLAS bundled inside); ours: `llama.cpp` build 12359, commit b1b770d90, compiled from source with CUDA 12.9 on the same guest. The kit build does not touch the system CUDA toolkit.

**Commands.**
```
LD_LIBRARY_PATH=$KIT/bin $KIT/bin/llama-bench \
  -m qwen3-coder-30b-a3b-q4_k_m.gguf -ngl 99 --n-cpu-moe 16 -p 512 -n 32 -r 5 -fa 0 -o json
/home/hermes/llama-new/build_v100/bin/llama-bench \
  -m qwen3-coder-30b-a3b-q4_k_m.gguf -ngl 99 -ncmoe 16 -p 512 -n 32 -r 5 -fa 0 -o json
```
Model: Qwen3-Coder-30B-A3B-Instruct Q4_K_M, 18.5 GB, expert layers partly in RAM (`-n-cpu-moe 16`), flash attention off (on sm_70 it is a known regression for MoE models). The GPU was idle (0 MiB used) before each run; the stand's cleanup script released the card first.

**Repeats.** Not recorded: repeatability was not documented for this run - treat the numbers as a single run unless the result says otherwise.

**Results.** Prefill (512 tokens): kit 645.1 ± 51.3 tok/s against 554.3 ± 5.2 for our build — 16 % higher. Decode (32 tokens): 57.1 ± 1.5 against 57.9 ± 1.1 — a 1.4 % difference, well inside both standard deviations. The kit binary loads the same GGUF without conversion, runs under driver 580, and needs no environment tricks beyond `LD_LIBRARY_PATH`. The package carries no sources, but it is a build of the public `ik_llama.cpp` tree at commit 022bd00a, so the numbers can be reproduced by compiling that commit.

**Verdict.** Mixed: prefill 16 % faster with the shipped sm_70 binaries, decode identical. Worth taking for long prompts (document analysis, repository context); not a reason to migrate a decode-bound workload. The vendor's agent wrapper (`serve-qwen3.sh`, Claude Code integration) and the claimed Gemma 4 26B-A4B QAT Q4_0 in 16 GB were not tested.

**Result type.** Mixed.

**Does not show.** One model, one quant, one set of flags: Q4_K_M with 16 expert layers in RAM, batch 2048/512, fp16 KV cache. The kit's spread is 8 % on prefill, so a 16 % gap is measured but not tight; decode equality rests on a 32-token run, which cannot show long-context degradation. Nothing here says the kit is faster on dense models, on other MoE shapes, or with flash attention enabled. The agent wrapper and the Gemma 4 claim remain unverified, and the archive ships prebuilt CUDA libraries that were not audited beyond "it starts and computes".

**Raw.** `raw/runs/V100-86.json` — both llama-bench runs (r=5 samples), build commits, flags, and the discarded warm-up run.
