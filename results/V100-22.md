# V100-22 — fni8 for LLM: int8 dp4a instead of tensor cores

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** The fni8 package claims that on the V100/CMP silicon part, fp16-tensor cores are disabled by the firmware, while integer dp4a is healthy (~46 TOPS). If this is true for our SXM2, then LLM can be considered not as "disabled" tensors but rather through integer means - and one weight format (.fni8) serves both DiT and LLM.

**Environment.** Tesla V100-SXM2-16GB (sm_70), driver 580, CUDA 12.9, guest VM on a home Proxmox host; engine: not recorded in the artifacts; model: not recorded in the artifacts.

**Commands.** Not run: the card was rejected after reading the sources, no experiment took place.

**Artifacts.** None, and none can exist: the card was rejected before any run.

**Repeats.** Not recorded: the field became mandatory only after this run, so repeatability is not documented - treat the numbers as a single run unless the result says otherwise.

**Result.** Rejected based on the author's documentation facts. fni8 (jajmangold/fni8, ComfyUI-fni8 package) is an int8 dp4a path through CUDA kernels, and it is designed for cards with **half-precision tensor cores disabled**: CMP 100-210 and similar mining Volta GPUs. The fni8 model README explicitly states: "Performance is fleet-specific. These numbers do not transfer to a real Tesla V100 (whose fp16 tensor cores would outperform dp4a)." We have a genuine Tesla V100-SXM2, and its fp16 cores are functioning normally: we measured this ourselves (V100-19 - 46 TOP/s on fp16 against 4.63 for the math-path GQA). Therefore, dp4a on CUDA kernels will be slower than our current fp16 trajectory, not faster. Additionally: the package covers DiT parts (Flux, SD3.5, Wan, LTX, Z-Image) and an LLM server separately (fni8-serve). Our working setup is SDXL through diffusers (Vae fp16, 13.3 seconds per frame) and llama.cpp for LLM; converting them to a foreign weight format `.fni8` for a path that is slower on our silicon makes no sense. Their quality is honestly stated as PSNR 29-31 dB, SSIM 0.95 - this is a visible loss for commercial photos. The same conclusion applies to V100-20 (the same package set for DiT).


**Verdict.** Rejected based on the author's documentation facts.

**Result type.** Negative.

**Does not show.** one run only - repeatability was not measured; the run log was not preserved, so the numbers cannot be re-checked from this repository.

**Raw.** Not preserved for this run.
