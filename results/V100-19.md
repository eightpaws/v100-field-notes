# V100-19 — GQA to MHA: the silent attention fallback that costs 7x

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Positive.

**Question.** On Volta, PyTorch scaled-dot-product attention with grouped-query attention cannot use the fused
kernel and quietly drops to the math backend — no exception, no warning, just a slower run. How large is the
penalty on this card, and does expanding K/V to full multi-head attention recover it?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Runtime | PyTorch 2.x + CUDA 12.x (video venv), ComfyUI attention selection |
| Measured shapes | attention at 8192 tokens, fp16 |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |

**Reproduce** (the measurement script was not preserved; this is the shape that produces the numbers):

```python
import torch
q = torch.randn(1, 32, 8192, 128, device="cuda", dtype=torch.float16)   # GQA: 8 KV heads
k = torch.randn(1, 8, 8192, 128, device="cuda", dtype=torch.float16)
v = torch.randn(1, 8, 8192, 128, device="cuda", dtype=torch.float16)
torch.backends.cuda.can_use_efficient_attention(q, k, v, 0.0, False, False)  # False on sm_70 for GQA

# forced comparison: same call with torch.nn.attention.sdpa_kernel(SDPBackend.MATH)
# expanded case: k/v repeated to 32 heads (MHA) before the call
```

**Results.**

| attention path | TF/s | note |
|---|---|---|
| GQA, auto selection | 4.63 | silently uses the math path; OOM at 8192 tokens |
| MHA | 33.15 | reference |
| GQA expanded to MHA | 31.9 | workaround, ×7.2 over the fallback |

**Repeats.** Single run per path, `n=1`.

**Verdict.** Check the attention path before blaming the pipeline: on sm_70 a GQA model can run 7x slower with no
error message, and the same shape then OOMs at 8192 tokens. Expanding K/V to MHA recovers almost all of it at the
cost of copied weights. LTX-Video, Wan, CogVideoX and SDXL on this rig are already MHA and unaffected — the rule
matters for GQA models (Qwen-VL class, newer video DiTs). Quick check: compare auto against forced MATH; if the
timings match, the fallback is active.

**Does not show.** Does not show an end-to-end speedup: no pipeline was timed before and after the K/V expansion, so ×7.2 is a kernel-level figure on one shape. The TF/s values and the 8192-token OOM come from a single run recorded in the run log, which was not preserved — treat them as reproducible-in-principle, not as archived evidence. The comparison against forced MATH is the part worth re-running first.
