# V100-76 — Ternary-Bonsai-2-27B: a 27B model in 6 GB on ternary weights

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: driver 580, CUDA 12.9, llama.cpp-derived `llama-server` built for sm_70._

**Repeats.** Not recorded: repeatability was not documented for this run - treat the numbers as a single run unless the result says otherwise.

**Result type.** Mixed — the ternary kernel path does execute on Volta, but code quality lands below the card's acceptance bar.

**Environment.** Tesla V100-SXM2-16GB (sm_70), driver 580, CUDA 12.9, context 8192 (4 slots of 4096), `-ngl 99`, `-fa off`; guest VM on a home Proxmox host. Model: `Ternary-Bonsai-2-27B-PTQ1_0.gguf`, 5,946,648,928 bytes, GGUF v3, 851 tensors, 26.9B parameters, 1.75 bits per weight.

**Question.** Ternary weights (type `PTQ1_0`) put a 27B model in 5.95 GB, against 13.6 GB for 27B in Q4. If the ternary kernels execute on Volta instead of falling back to CPU, we get a much larger model without evicting layers into RAM.

**Commands.**

```
# what the engine was asked to do (flags from the server log and run artifacts)
llama-server -m /srv/media/ai-cache/downloads/bonsai27b/Ternary-Bonsai-2-27B-PTQ1_0.gguf \
  -ngl 99 -c 8192 --host 127.0.0.1 --port 18462

# the failure path recorded in raw/runs/V100-76.json
llama-bench -m <model> -ngl 99 -p 32 -n 8 -r 1        # abort: no tensor-core path for cc 700
llama-bench -m <model> -ngl 0  -p 64 -n 16 -r 1       # CPU reference: 29.06 pp, 0.47 tg
```

The exact server command line was not preserved verbatim; flags above are those recorded in the server log and in the card.

**Results.**

| What | Value | Source |
|---|---|---|
| decode (tg), 8k context | **65.19–65.25 tok/s** | `bonsai_server.log`, consecutive tasks |
| prompt eval, 97 tokens | 166.73 tok/s (0.58 s) | `bonsai_server.log` |
| model start | 4.0 s | `bonsai_server.log`, `eval_bonsai.json` |
| code battery, 40 tasks | **pass@1 0.325 (13/40)**, avg 7.4 s, wall 296.8 s | `eval_bonsai.json` |
| CPU reference, same file | 29.06 tok/s prompt, **0.47 tok/s** decode | `raw/runs/V100-76.json` |

Stock llama.cpp cannot open the file at all (`failed to read tensor info`, tensor type 143). The `xyznq1/xyz-llama` fork (HEAD f095f4d) aborts on this GPU with `ggml-cuda/mmvq.cu:1273: PTQ1_0 ILV16: no tensor-core path for this call (ids=0, ncols=1, cc=700)`; the same file on CPU decodes at 0.47 tok/s. A patched build (PrismML-Eng llama.cpp plus three UI-asset edits so `llama-server` links) loads the file and serves it at the 65 tok/s above — a 140× gap against the CPU path, so the ternary kernels are executing on the Volta SMs, not on the CPU.

**Verdict.** Ternary kernels work on sm_70 once the server actually builds, and 27B fits in roughly 6.8 GB of VRAM at 8k context. Quality does not carry it: 0.325 pass@1 on the 40-task code battery, below the 0.5 threshold set in the card and well below the 0.625 of Qwen2.5-Coder-7B Q8. Useful where memory is the binding constraint, not where code correctness is.

**Does not show.** Only the code battery was measured — no tool calling, no long-context needle, no comparison against a dense model of similar size on the same harness. VRAM was not logged by the server (the 6.8 GB figure comes from the card, not from an artifact). The numbers `pp256 814.3 ± 11.9` and `tg64 67.44 ± 0.11` that stood in the card earlier are **not reproducible from any saved artifact**: `llama-bench` died in `llama_decode` (segfault) and `bonsai_bench.log` holds only the CUDA init banner. Everything above is a single run.
