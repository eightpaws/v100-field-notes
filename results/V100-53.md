# V100-53 - Cache prefix: equal comparison at equal prompt length

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Does the prefix-cache win survive when prompt length is held equal? The earlier card (V100-11) compared a 3368-token cold run against a 5045-token uncached run, so its "8x" could have been a length artifact.

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB (sm_70), 16 GB HBM2 |
| Driver | 580.178.04 |
| Engine | llama-server 1.0.0-dev, build129, commit af5c583 |
| CUDA toolkit | 12.9 |
| Model | qwen2.5-7b-instruct.gguf (Q4) |
| Server flags | `-c 16384 -np 1 --cache-reuse 256` |

**Commands.**

```
/root/bin/v100-run.sh V100-53 -- bash /root/v53_driver.sh
```

Inside the driver, verbatim:

```
llama-server -m /models/qwen2.5-7b-instruct.gguf -ngl 99 -c 16384 -np 1 \
  --cache-reuse 256 --port 18353 --host 127.0.0.1
```

The harness (`/root/v53_harness2.py`) sends `POST /completion` with `n_predict: 1`, `temperature: 0`, `top_k: 1` and reads `prompt_ms`, `prompt_n` and `cache_n` from the `timings` block. Prompt length was fixed by measuring `prompt_n` in the response, not by character counting.

**Result.**

| Window, tokens | No cache | Repeat (cache) | Tail edit | Gain |
|---|---|---|---|---|
| 2053 | 575.0 ± 1.6 ms | 77.4 ± 1.0 ms | 80.0 ± 2.3 ms | 7.4x |
| 6142 | 1916.2 ± 3.4 ms | 208.5 ± 1.5 ms | 213.8 ± 1.2 ms | 9.2x |
| 12288 | 4516.7 ± 8.4 ms | 409.0 ± 3.4 ms | 410.0 ± 2.2 ms | 11.0x |

Prefill throughput was 3571 tok/s at the 2k window and 2720 tok/s at 12k. The first cold run of the 2k window included model warm-up (609.3 ± 41.0 ms), so the no-cache series is used as the baseline. A cold probe with a unique head (nothing reusable) matched the no-cache numbers, which confirms that `cache_prompt: false` really disables reuse. A tail edit costs the same as a plain repeat: the unchanged prefix is reused in full.

**Verdict.** At equal prompt length the prefix cache still wins 7.4x at 2k, 9.2x at 6k and 11.0x at 12k, and the gain grows with context instead of shrinking. The "8x" reported in V100-11 was an understatement, not an artifact of the different prompt lengths.

**Result type.** Positive.

**Does not show.** One model (7B Q4) and one server process at `-np 1`; user-visible time-to-first-token through a chat client was not measured; Ollama was not re-measured at equal lengths, so its older numbers stand unchanged; no second engine or quantisation level was compared on this harness.

**Repeats.** n=3 per window and scenario, mean ± stdev.

**Artifacts.** `/root/runs/V100-53/run.log` on the rig; JSON copy in this repository.
