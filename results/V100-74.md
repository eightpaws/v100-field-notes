# V100-74 - Olala-v1.0-mini-7A1B: a fork loads the 7B MoE, but the output is degenerate

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a VM: 24 vCPU, driver 580.178.04, Ubuntu 24.04._

**Question.** A 7B MoE with 1B active parameters in q5_k_m weighs about 6 GB and should be the shape that
DeepSeek-Coder-V2-Lite turns into 183 tok/s on this card. Does a 7B/1B-active MoE reach 140+ tok/s at better
quality than a dense 7B, and is the model usable at all through llama.cpp?

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, sm_70 (compute capability 7.0) |
| Driver / OS | 580.178.04, Ubuntu 24.04 |
| CUDA toolkit | 12.9, installed without root in `~/cuda-12.9` (the system 12.0 cannot build these kernels) |
| Engine | community fork of llama.cpp, commit `bd20ca9`, built Release with `CMAKE_CUDA_ARCHITECTURES=70` |
| Model | `Olala-v1.0-mini-7A1B-q5_k_m.gguf`, 5 990 551 040 bytes (size checked against the file listing), 6.78 B params |
| Server flags | `--jinja -fa 0 -np 1` |

Three attempts, in order. Upstream llama.cpp master of 24.11 refused the file outright with
`unknown model architecture: 'olala'`, so the file was intact but unreadable. A community fork that carries an
`olala` architecture implementation loads it, and everything below comes from that fork.

**Commands.**

```
# server (GPU)
./llama-server -m /srv/media/ai-cache/downloads/olala7a1b/Olala-v1.0-mini-7A1B-q5_k_m.gguf \
  -ngl 99 -fa 0 -c 32768 -np 1 --port 18481 --host 127.0.0.1 --jinja

# benchmark, three repeats
./llama-bench -m <same file> -p 256 -n 64 -r 3

# quality
python3 /root/code_eval.py --base-url http://127.0.0.1:18481 --model olala --tasks 40

# CPU control: same binary, no offload
./llama-server -m <same file> -ngl 0 -c 4096 -t 16 --port 18482 --jinja
```

**Results.**

| Metric | Value | Unit |
|---|---|---|
| Model size | 5 990 551 040 | bytes |
| Server start | 17.7 | s |
| Prefill pp256 | 783.66 ± 5.10 | tok/s |
| Decode tg64 | 43.52 ± 0.18 | tok/s |
| Decode on the 27.11 smoke run | 40-41 | tok/s |
| VRAM at 8k context | 6 583 | MiB |
| VRAM at 32k context | 10 541 | MiB |
| MBPP pass@1 (40 tasks, default template) | 0.0 (0/40) | - |

The speed is real and the memory footprint is good. The text is not. At temperature 0, the prompt
`1, 2, 3, 4,` comes back as `2, 2, 2, 2`, and `The capital of France is` produces
` Paris. The capital of France. The capital of France...` until the token limit. At temperature 0.6 with
top_k 20 the answer is incoherent prose, and `/v1/chat/completions` returns an empty `content` with
`finish_reason: length` (the text lands in the reasoning field). The same three probes on the CPU
(`-ngl 0`, no CUDA path at all) degrade the same way, so the fault is in the architecture implementation in
the fork, not in the CUDA kernels or in the card.

**Result.** The model loads and decodes at 43.5 tok/s with 6.6 GB resident, but no probe produced usable
text, on GPU or CPU. The card's bar - pass@1 >= 0.55 at >= 140 tok/s - is not met on either count, and the
MBPP score of 0/40 is an artifact of broken output rather than a statement about model quality.

**Repeats.** `llama-bench` with three repeats for pp256 and tg64 (standard deviation above); MBPP is a
single run over 40 tasks; the degeneration probes were run three times per configuration (temperature 0 and
0.6). No repeat of the full quality harness: it measures broken text.

**Verdict.** A community fork loads the model and decodes at 43.5 tok/s, but the output is degenerate on GPU and CPU alike, so the model is unusable on this stack and its quality stays unmeasured.

**Result type.** Negative.

**Does not show.** Model quality: with broken output, MBPP 0/40 says nothing about the model and no other
quality check was possible. Whether upstream llama.cpp has learned the `olala` architecture since - the
attempt above is a snapshot, and upstream support is the natural way to re-run this. Whether a different
quant or a different template would fix the degeneration: one quant was tested, and the loop reproduces on
CPU, which points at the code rather than at the weights. No baseline model was measured on the same prompts
in the same session.

**Raw.** `raw/runs/V100-74.json` - the 24.11 attempt (architecture refusal, size check) and the bench numbers
of the 26.11 run. The 27.11 smoke probes are not archived as JSON: their logs are
`/root/runs/V100-74/server.log`, `server_cpu.log`, `smoke_default.json`, `smoke_nothink.json` on the rig.
Drivers: `/root/code_eval.py` for MBPP.

**Follow-up.** Re-check when upstream llama.cpp accepts the `olala` architecture; the file is already on
disk, so a re-run costs one harness pass, not a download.
