# V100-74 - Olala-v1.0-mini-7A1B: MoE with 1B active on a 16 GB card

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a VM: driver 580.178.04, CUDA 12.9, 24 vCPU, 94 GiB RAM._

**Question.** A 7B-class MoE with ~1B active parameters weighs 6 GiB at q5_k_m, and the same shape gave
183 tok/s on DeepSeek-Coder-V2-Lite. Does this one deliver 140+ tok/s with better quality than a dense 7B?

**Environment.** V100-SXM2-16GB (sm_70), CUDA 12.9. The GGUF declares `general.architecture = olala`,
which upstream llama.cpp rejects outright ("unknown model architecture"), so the model was run on its own
fork: `OVHai-LLM/llama.cpp`, branch `olala-master`, HEAD `bd20ca9`, built locally with
`-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70`. Weights `Olala-v1.0-mini-7A1B-q5_k_m.gguf`,
5 990 551 040 bytes, 6.78 B parameters, 5.57 GiB.

**Commands.**
```
git clone --depth 1 -b olala-master https://github.com/OVHai-LLM/llama.cpp /root/llama-olala
cmake -S /root/llama-olala -B /root/llama-olala/build -DGGML_CUDA=ON \
      -DCMAKE_CUDA_ARCHITECTURES=70 -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build /root/llama-olala/build -j 20 --target llama-bench llama-server
./build/bin/llama-bench -m Olala-v1.0-mini-7A1B-q5_k_m.gguf -p 256 -n 64 -r 3
./build/bin/llama-server -m ... -ngl 99 -c 8192 --host 127.0.0.1 --port 18480 -t 8 --jinja
python3 /root/code_eval.py --base-url http://127.0.0.1:18480 --model olala --tasks 40 --max-tokens 1600
```

**Repeats.** `llama-bench -r 3` for both prefill and decode; the quality runs are single runs.

**Result.** The fork loads the file and runs it: prefill **783.66 +/- 5.10 tok/s** on pp256, decode
**43.52 +/- 0.18 tok/s** on tg64, and the server holds **6 583 MiB** - less than half the card, as the
parameter count promised. Speed does not come close to the 140 tok/s the hypothesis required; the dense
7B on the same card already does 105 tok/s, so the MoE shape bought memory headroom, not speed.
Quality could not be established: the model puts its whole chain of thought into `reasoning_content`,
leaving `content` empty at the default template and `finish_reason=length`, and with
`chat_template_kwargs.enable_thinking=false` the reasoning prose simply moves into `content`. The MBPP
harness therefore scored 0.0 on 40 tasks (empty answers) and the 20-task follow-up died when the server
went down mid-batch.

**Verdict.** Negative on the card's own criterion: 43.5 tok/s against a 140 tok/s bar, and no usable
quality number. Keeping the model makes sense only if its chat template is rewritten so answers arrive
without the think-aloud preamble; nothing else here justifies the extra fork in the stack.

**Result type.** Unstated - the result reports measurements without an explicit pass/fail verdict.

**Does not show.** No valid code score at all - the template problem masks whatever quality the model has,
so a future run with a fixed template could still change the verdict on quality, though not on speed.
Prompt-processing of long contexts and tool calling were not exercised.

**Raw.** `raw/runs/V100-74.json` - bench numbers, VRAM, chat-template behaviour, both MBPP attempts.
