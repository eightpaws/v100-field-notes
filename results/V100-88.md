# V100-88 - Flash-Attention-V100: FA2 fork for vLLM cannot be selected on sm_70

_Measured on a Tesla V100-SXM2 16 GB (sm_70), driver 580.178.04, inside a Proxmox VM with 24 vCPU and 94 GiB RAM._

**Question.** A community FlashAttention-2 port for SM70 (`zhinianqin/flash-attention-v100`) claims +580% over TRITON_ATTN on 8k prompts. Can that backend be plugged into 1Cat-vLLM 1.5.4 on this card, and does prefill at 8k and 16k grow by more than 30%?

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute capability 7.0, 16 GiB |
| Driver / CUDA toolkit | 580.178.04 / 12.9 (built only for `sm_70`) |
| Engine | vLLM 1.5.4 (1Cat build), torch 2.10.0+cu128 |
| OS / CPU | Ubuntu 24.04.5, 24 vCPU |
| Host compiler | g++-12 (`CUDAHOSTCXX`), nvcc 12.9 |
| Model | Qwen2.5-7B-Instruct GGUF, 5.44 GB, `load_format=gguf`, KV cache `int8_per_token_head` |
| Server flags | `--max-model-len 17408 --no-enable-prefix-caching --gpu-memory-utilization 0.90` |
| VRAM at steady state | 15 103 MiB of 16 384 MiB |
| Server start | 105-138 s per arm |

**Commands.**

```bash
# build of the fork (CUDA 12.9, sm_70 only, g++-12 as host compiler)
cd /root/fa-v100 && CUDAHOSTCXX=/usr/bin/g++-12 cmake --build build/temp.linux-x86_64-cpython-312 --target=_vllm_fa2_C -j 5
cp build/temp.linux-x86_64-cpython-312/_vllm_fa2_C.abi3.so /home/hermes/venvs/vllm/lib/python3.12/site-packages/vllm_flash_attn/

# one arm per backend
VLLM_ATTENTION_BACKEND=TRITON_ATTN /home/hermes/venvs/vllm/bin/python -m vllm.entrypoints.openai.api_server \
  --model /models/qwen2.5-7b-instruct.gguf --served-model-name qwen25-7b --max-model-len 17408 \
  --no-enable-prefix-caching --gpu-memory-utilization 0.90 --port 18511 --host 127.0.0.1

python3 /root/bench_v88b.py 18511 /srv/media/night/v100_88.jsonl TRITON_ATTN 8192 16384
```

The same two steps were repeated with `VLLM_ATTENTION_BACKEND=FLASH_ATTN_V100` (port 18512) and `VLLM_ATTENTION_BACKEND=FLASH_ATTN` (port 18513).

**Results.** Prefill throughput measured as wall time of a single-token completion, prompt length taken from `usage.prompt_tokens`.

| Arm (`VLLM_ATTENTION_BACKEND`) | Backend actually selected | 8 190 tokens | 16 384 tokens |
|---|---|---|---|
| TRITON_ATTN | FLASH_ATTN_V100 | 1 091 tok/s (7.51 s) | 623 tok/s (26.28 s) |
| FLASH_ATTN_V100 | FLASH_ATTN_V100 | 1 091 tok/s (7.51 s) | 623 tok/s (26.28 s) |
| FLASH_ATTN (fork) | FLASH_ATTN_V100 | 1 091 tok/s (7.51 s) | 623 tok/s (26.28 s) |

All three arms printed the same selector line: `Using FLASH_ATTN_V100 attention backend out of potential backends: ['FLASH_ATTN_V100', 'TRITON_ATTN']`. On compute capability 7.0 the platform offers only `FLASH_ATTN_V100`, `TRITON_ATTN`, `FLEX_ATTENTION` and `TURBOQUANT`; the fork's `FLASH_ATTN` is not among them, and `VLLM_ATTENTION_BACKEND` acts as an allow-list, not a forced choice. The built extension imports without error (`_vllm_fa2_C.abi3.so`, 240.7 MB) but never runs.

**Repeats.** n=3 per length, first repeat discarded as warm-up. Warm repeats differ by less than 0.02% (e.g. 7 507.9 and 7 507.8 ms at 8k), so the spread is far below any effect this test could have detected.

**Result.** Prefill on the backend the engine actually runs: 1 091 tok/s at 8 190 tokens, 623 tok/s at 16 384 tokens. Between 8k and 16k the throughput falls by 43%, consistent with a quadratic attention term once the prompt outgrows the tile-friendly range. The fork produced no measurement of its own: every arm was served by the same backend.

**Verdict.** Negative for the claim as stated: the FA2 fork builds and imports on sm_70 but cannot be selected in this engine, so the promised +580% over Triton is untestable here without patching backend selection in the platform; the stock Volta backend gives 1 091 tok/s at 8k and 623 tok/s at 16k.

**Result type.** Negative.

**Does not show.** No Triton-only baseline exists: the env var did not force Triton, so "1 091 tok/s" is the 1Cat Volta backend, not TRITON_ATTN. Quality was not measured (a single-token completion cannot show it), the fork's kernels never ran (so nothing is known about their correctness or speed), and one model at one KV-cache dtype was used.
