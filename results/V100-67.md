# V100-67 — 16 GB: Q4_K_M - 128 bits, Q5_K_M - 160 bits, Q6_K - 256 bits, Q8 - 320 bits

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** For the 7B model, any quantum can fit on the map, but it is unknown how much quality is lost on Q4 and where the boundary is beyond which memory ends.

**Environment.** llama.cpp, Qwen2.5-Coder-7B in Q4_K_M / Q5_K_M / Q6_K / Q8_0, MBPP 40 tasks; V100 16 GB (sm_70), driver 580, CUDA 12.9

**Commands.** The run script was not preserved; the runner was `/root/bin/v100-run.sh V100-NN`.

**Artifacts.** Logs were not preserved for this run.

**Repeats.** single run

Q5 wins 3 out of 40 tasks (+7.5 pp), which is close to noise (one task = 2.5 pp), so the conclusion is cautious: **Q5_K_M - a reasonable compromise, Q4_K_M - when maximum speed is needed, Q6_K - pointless**. Q8_0 is still training. **Quality profile does not depend on quant.** Full runs on other blocks with Q4, Q5, and Q6 showed the same result: format **0.8** (4/5), RAG **0.5** (misses 14-day window), content failed (324-419 words ordered 550-650), tools 0 calls (no template), honesty, stability, and long context passed. So, quant choice affects code and speed, not discipline and tendency to fabricate. Measurement was done on a free card (gpt-oss was down at the time), single repeats, so prefills between quants are roughly compared: Q4's figure was taken on a different prompt (pp512).
