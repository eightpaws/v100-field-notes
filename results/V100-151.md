# V100-151 — PXQN vs standard Q4_K_M on a single 27B

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Proprietary PXQN4 (3.97 bits per weight) promises 27B in 16 GB; standard Q4_K_M of the same Qwen3.8-27B is nearly the same size and loads with stock llama.cpp - if quality and speed match, the only purpose of PXQN is support for sm_70.

**Environment.** Stock llama.cpp build af5c583 (`/home/hermes/llama-new/build129`, CUDA 12.9), Tesla V100-SXM2-16GB sm_70, driver 580.178.04, guest VM on local workstation, Ubuntu 24.04; model unsloth/Qwen3.8-27B-GGUF UD-Q4_K_M, file 16,564,259,744 B; comparison line - PXA 4.0.4 from V100-148

**Commands.** ```bash v100-run.sh V100-151 -- bash /root/v151_driver.sh Inside bench: env LD_LIBRARY_PATH=/home/hermes/llama-new/build129/bin llama-bench -m <gguf> -ngl 99 -p 256 -n 128 -r 3 -b 2048 -ub 512 Quality: llama-server -m <gguf> -ngl 99 -c 4096 --port 18096 -t 16 -np 1 --no-webui Plus: python3 /root/code_eval.py --base-url http://127.0.0.1:18096 --model qwen38-27b-q4km --tasks 40 --no-think --max-tokens 1536 --temperature 0 --out /srv/media/night/v100_151_q4km.json Repeat - separate run: V100-151b with port 18097 ```

**Result.** The default Q4_K_M of the same Qwen3.8-27B model fully loads onto the card using the stock llama.cpp and achieves a MBPP pass@1 score of **0.650 (26/40)** compared to 0.600-0.625 (24-25/40) of two PXQN checkpoints, which is one to two tasks more but 2.2-4.2 times slower: 33.9 tok/s in the encoder and 38.63 tok/s decoding against 75.5-76.7 and 162 for PXQN. It fits with a context of 4096: peak at 15,909 MiB out of 16,144, reserve 235 MiB, rise 8s. Conclusion: The proprietary codec PXQN4 buys speed over quality, and the default 27B in Q4_K_M works on this card but is 34 tok/s below 76 tok/s of the 30B MoE with eviction.

**Does not show.** Comparison with PXQN field - different engine and different run (V100-148), A/B not done in one harness; only Python and MBPP on 40 tasks, one task = 2.5 pp., thus +1-2 tasks do not prove quality advantage; contexts 8k and 32k not measured - at 4096 already occupied 15,909 MiB of 16,144; reason for fourfold decode difference (PXQN dequant-free codec against Q4_K-cores on sm_70) not profiled, it's a hypothesis.
