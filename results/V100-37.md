# V100-37 - 32B dense vs 30B MoE: decode re-measured on 94 GiB of RAM

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Negative.

**Question.** Earlier notes said "qwen2.5-32b gives 7 tok/s, offloading to RAM kills speed" and "30B-A3B gives
35 tok/s hybrid", but those runs happened when the VM had 32 GB of RAM filled to the ceiling, so the CPU-resident
weights were fighting the page cache instead of staying resident. With 94 GiB, is the wall still the card?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine | llama.cpp 1.1.0-dev, build `28148b5`, `llama-bench` built for sm_70 |
| Models | qwen2.5-32b-instruct Q4_K_M (18.48 GiB, 32.76 B dense) and qwen3-30b-a3b Q4_K_M (17.28 GiB, 30.53 B, 3 B active) |
| Host | Proxmox VE VM: 24 vCPU (EPYC 7282), 94 GiB RAM (92 GiB available, 88 GiB file cache), Ubuntu 24.04.5, kernel 6.8.0-151 |
| Toolchain | CUDA 12.9 in a user-space toolkit, driver 580.178.04 |
| Variable | `-ngl` = 20 and 99 |

**Commands** (verbatim, run through the card runner so the log and PID are real):

```bash
/root/bin/v100-run.sh V100-37 -- bash /root/v37b.sh

# inside the driver, reps 3 for the working configuration
llama-bench -m /models/qwen2.5-32b-instruct.gguf -ngl 20 -p 512 -n 64 -r 3
llama-bench -m /models/qwen3-30b-a3b.gguf        -ngl 20 -p 512 -n 64 -r 3
# then both models with -ngl 99, one rep: the expected refusal
llama-bench -m /models/qwen2.5-32b-instruct.gguf -ngl 99 -p 512 -n 64 -r 1
llama-bench -m /models/qwen3-30b-a3b.gguf        -ngl 99 -p 512 -n 64 -r 1

# second pass (card V100-37b) samples VRAM every 2 s while one rep runs
nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits
```

**Results** (run of 2026-11-28, `n=3`, mean +/- stdev as printed by `llama-bench`).

| model | file, GiB | `-ngl` | prefill pp512, tok/s | decode tg64, tok/s | VRAM peak, MiB |
|---|---|---|---|---|---|
| qwen2.5-32b Q4_K_M (dense) | 18.48 | 20 | 247.5 +/- 18.2 | **3.86 +/- 0.12** | 7 101 |
| qwen2.5-32b Q4_K_M (dense) | 18.48 | 99 | - | does not load: `cudaMalloc failed`, 18 508 MiB requested | - |
| qwen3-30b-a3b Q4_K_M (MoE) | 17.28 | 20 | 512.6 +/- 18.1 | **31.51 +/- 0.72** | 7 923 |
| qwen3-30b-a3b Q4_K_M (MoE) | 17.28 | 99 | - | does not load: `cudaMalloc failed`, 17 524 MiB requested | - |

Earlier run of 2026-11-22 on the same host, different build and flags (`-n 128 -fa 1 -r 2`): dense 32B 3.0 tok/s
at `-ngl 20` and 253.2 tok/s prefill; MoE 24.5 tok/s and 439.7 tok/s; `-ngl 40` and `-ngl 99` refused to load.
The order of magnitude is the same, so the two runs agree; they are not like-for-like and are not averaged.

**Repeats.** Three repetitions per configuration (`-r 3`, decode and prefill), spread as printed above: +/- 0.12
tok/s on dense decode and +/- 0.72 on MoE decode. The `-ngl 99` refusals are single runs - a failure does not
need repeats. The VRAM peaks are single runs each.

**Verdict.** System RAM is not the wall: with 94 GiB the dense 32B still decodes at 3.9 tok/s and the 30B MoE at
31.5 tok/s, so on 16 GB load a 30B MoE or stay at 14B dense; dense 30B+ is not worth the download.

**Does not show.** The bench runs without a KV cache (`-p 512 -n 64`), so in a real 4-8k chat the decode will be
lower and the MoE may already refuse 8k context. `-ngl 40` was not retried in this run, so the exact layer
boundary between 20 and 99 is still unknown. Process RSS was not sampled - only VRAM - and Ollama with
`num_gpu`/`num_cpu` was not re-measured at all, so this card speaks only about `llama-bench`.

**Follow-up.** Queued as V100-55 (capture stderr to explain the layer refusal); that run now has the answer for
`-ngl 99` - allocation of 17.5-18.5 GiB against 16 GiB of VRAM - and the 20-to-99 boundary is still untested.
