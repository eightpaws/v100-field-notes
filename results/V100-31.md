# V100-31 - One 27B model across V100 and 4060 Ti: pipeline split works, and costs 25-40 %

Card V100-31, priority P0: use the V100 plus the PC's 4060 Ti as one pool for a single 27B-class model. Tensor-parallel arithmetic over the 1 Gbit link rules itself out (11 tok/s ceiling from latency alone), but a layer split does not need per-token all-reduce, and llama.cpp ships one: the RPC backend. Measured: a 27B model split across both machines decodes at 21-27 tok/s against 35 tok/s on the V100 alone, so the pool works and is 1.3-1.7x slower than one card.

## Question

Can the V100 (16 GB, sm_70) and the RTX 4060 Ti (16 GB, sm_89) on a second machine serve one 27B-class model as a single pool, and what does the network cost per generated token?

## Environment

| Item | Value |
|---|---|
| GPU A | Tesla V100-SXM2 16 GB, compute capability 7.0, driver 580, 900 GB/s |
| GPU B | RTX 4060 Ti 16 GB, compute capability 8.9, driver 617.14, 288 GB/s |
| Host A | GPU VM on the home Proxmox node, Ubuntu 24.04, 24 vCPU, 94 GiB RAM |
| Host B | Windows 11 desktop |
| Network | 1 Gbit switched LAN, no RDMA, no NVLink |
| Engine | llama.cpp `b1b770d` rebuilt with `-DGGML_RPC=ON`; official `ggml-rpc-server` `b12816` win-cuda-12.4 on the PC |
| RPC protocol | 10.0 on both sides, no version skew |
| Model | `Qwen3.8-27B-GSQ-RCO-IQ3_S`, 10.95 GiB, 3.4375 bpw, context 4096 |

## Commands

```bash
# PC side: expose the 4060 Ti as an RPC device
ggml-rpc-server.exe -H 0.0.0.0 -p 50052 -c

# GPU guest: split the model across CUDA0 (V100) and the remote device
llama-server -m /srv/media/models/qwen38-27b/Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf \
  -c 4096 -ngl 999 --port 18111 --rpc <pc-lan-address>:50052 -ts 0.5,0.5
python3 /root/v148_speed2.py 18111 rpc_50_50 256

# baseline, same model and same harness, one card only
llama-bench -m <same file> -p 256 -n 64 -r 3 -ngl 99
```

`-ts` fractions follow the device order, and on this rig the RPC device is listed first: `0.65,0.35` puts 65 % on the PC, which the VRAM column in the results makes obvious.

## Results

| Configuration | Layers on V100 | Layers on 4060 Ti | Decode, tok/s | vs one card | VRAM on V100, MiB |
|---|---|---|---|---|---|
| all on V100 (no `--rpc`) | 100 % | 0 | 35.3 | 1.00 | 12 197 |
| `-ts 0.35,0.65` | 65 % | 35 % | 26.5 | 0.75 | 8 741 |
| `-ts 0.50,0.50` | 50 % | 50 % | 22.9 | 0.65 | 7 035 |
| `-ts 0.65,0.35` | 35 % | 65 % | 21.3 | 0.60 | 5 201 |
| `llama-bench` tg64, all on V100 (reference) | 100 % | 0 | 37.1 ± 0.06 | 1.05 | - |

Decode is read from the server's own `timings.predicted_ms`, 256 generated tokens, three repeats each, temperature 0. The more layers stay on the V100 the faster the pool runs: 900 GB/s against 288 GB/s, plus one crossing of the 1 Gbit link per token for the remote share.

Link measurements that the earlier edition of this card was built on still stand:

| Metric | Value | n |
|---|---|---|
| Single-stream TCP throughput | 117.4 MB/s (939 Mbit/s) | 3 |
| TCP connect RTT, median | 0.32 ms (p90 0.48) | 30 |
| Echo round trip, 10 KB | 0.688 ms median | 200 |
| Echo round trip, 1 MB | 21.7 ms median | 200 |

Tensor-parallel arithmetic for a 27B dense model split two ways (64 layers, two all-reduces per layer, fp16 activations of 5120 units, 128 collectives and 2.62 MB per token) gives a latency ceiling of **11.4 tok/s** and a bandwidth ceiling of **44.8 tok/s**. A layer split, which is what llama.cpp's RPC backend does, exchanges only the hidden state at layer boundaries and never pays 128 collectives per token - that is why the measured 21-27 tok/s beats the TP ceiling by 2x.

## Repeats

Decode n=3 per configuration (spread inside 1 %); baseline additionally measured with `llama-bench -r 3` (37.12 ± 0.06 tok/s tg64, 508.9 ± 5.2 tok/s pp256). Network figures from the earlier edition: throughput n=3, echo RTT n=300 independently reproduced (107.0 MB/s, 0.677 ms median).

**Verdict.** A layer split across two machines is possible on this hardware without vLLM: rebuild llama.cpp with `GGML_RPC`, run `ggml-rpc-server` on the Windows PC, and the guest's `llama-server --rpc <ip>:50052 -ts ...` spreads a 27B model over both cards. It costs 25-40 % of decode speed against one card, so for a model that already fits in 16 GB the pool is a pure loss; the case where it should pay - a quant that does not fit one card - was not measured here.

**Result type.** Mixed.

## Does not show

- Prefill on the split configuration was not measured, only decode.
- Quality was not re-checked across the RPC backend: the same file loads, but the compute path differs and outputs were not compared token by token.
- Stability over 30 minutes and behaviour when the PC drops out were not tested; the PC answered throughout.
- No quant larger than IQ3_S was tried, so "the second card buys a 27B that otherwise does not fit" remains a hypothesis for a Q5/Q6 file.
- The RPC server was exposed on 0.0.0.0 without authentication, acceptable only inside a home LAN.
