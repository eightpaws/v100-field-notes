# V100-31 - One model across V100 and 4060 Ti: the link kills it

Card V100-31, priority P0: run a single 27B-class model on the V100 plus the PC's 4060 Ti as one pool, in the hope that 32 GB of VRAM buys a bigger model than a single card allows. Answer: no. The 1 Gbit link between the machines caps tensor-parallel decode far below what one V100 already delivers on a 30B MoE.

## Question

Can the V100 (16 GB, sm_70) and the RTX 4060 Ti (16 GB, sm_89) on a second machine serve one 27B-class model through tensor parallelism over the home LAN, and is the result faster than a single-card model that fits today?

| GPU B | RTX 4060 Ti 16 GB, compute capability 8.9, driver 617.14 |

| Tooling | `curl` 8.x, Python 3.12 `http.server`, a 22-line TCP echo server with `TCP_NODELAY` |
| Model run | none - the card was closed on link arithmetic before any 27B weights were loaded |

## Commands

```
# 512 MB test file on the GPU guest, served over HTTP from the guest
ssh root@<guest> 'dd if=/dev/zero of=/srv/media/night/net_test_512m.bin bs=1M count=512'
ssh root@<guest> 'python3 -m http.server 18999 --bind 0.0.0.0 --directory /srv/media'

# throughput, three runs, written to NUL (a POSIX /dev/null sink fails on Windows curl)
curl -sS -o NUL -w "%{speed_download}\n" http://<guest>:18999/night/net_test_512m.bin

# connection latency, 30 connects to the guest ssh port
python -c "socket connect loop, perf_counter per connect"

# request-response latency: 200 round trips per payload size
python -c "sendall(4-byte length + payload); recv loop; TCP_NODELAY on"
```

## Results

| Metric | Value | n |
|---|---|---|
| Single-stream TCP throughput | **117.4 MB/s (939 Mbit/s)** | 3 |
| TCP connect RTT, median | 0.32 ms (p90 0.48) | 30 |
| Echo round trip, 10 KB | 0.688 ms median | 200 |
| Echo round trip, 100 KB | 2.52 ms median | 200 |
| Echo round trip, 1 MB | 21.7 ms median | 200 |

Tensor-parallel arithmetics for a 27B dense model split two ways: 64 layers, two all-reduces per layer, fp16 activations of 5120 hidden units, so 128 collectives and 2.62 MB of exchange per generated token.

| Bound | Assumption | Ceiling |
|---|---|---|
| Latency | every collective pays one measured 10 KB round trip (0.688 ms) | **11.4 tok/s** |
| Bandwidth | all 2.62 MB/token flow at 117.4 MB/s | 44.8 tok/s |

Reference point on the same V100 alone: Qwen3-Coder-30B-A3B at `-ncmoe 8` decodes **24.5 tok/s**, and a 14B fits with room for 32k context.

The premise of the card also failed on shape rather than on existence: `volta-ada` does exist in the fork `0ics-srls/1Cat-vLLM` (branches `volta-ada`, `volta-ada-tp`, `volta-ada-mtp-pp`), but the fork's own description reads "runs one model on a V100 + RTX 4090 pipeline, with the per-arch Marlin FP4 fix" - pipeline parallelism inside one machine with a 4090, not tensor parallelism across a network. The fork's design notes are blunter about the card's second card: the 8 GB SM89 4060 Ti "cannot host the TP2 27B route" and is used there only as an operator-registration probe.

## Repeats

Throughput n=3 (one 512 MB file per run, page cache warm), connect RTT n=30, echo RTT n=200 per payload size. A second independent run on the same day reproduced the link: 107.0 MB/s single stream (419 MB in 3.9 s) and 0.677 ms median for a 10 KB round trip, n=300. The model ceilings are arithmetic on the measured medians, not a measured decode.

## Verdict

**Verdict.** Heterogeneous tensor parallelism over 1 Gbit is latency-bound at roughly 11 tok/s for a 27B dense model, and even the bandwidth-only ceiling (45 tok/s) leaves no margin over the 24.5 tok/s that one V100 already gives on a 30B MoE that fits. A 32 GB pool built across two machines does not turn into a faster or larger usable model here: the fork's `volta-ada` route is a V100 + 4090 pipeline inside one machine rather than a network TP path, and the PC side would need Linux under Windows to run vLLM at all.

**Repeats.** Single run, not repeated.

**Result type.** Negative.

## Does not show

- No 27B model was ever loaded on two cards: the ceiling comes from measured exchange latency, not from NCCL, which pipelines collectives and would land somewhere between the two bounds.
- vLLM on the PC side was never attempted. vLLM needs Linux, the PC runs Windows, so the target configuration would need WSL2 with GPU passthrough - a cost this card does not price.
- The same measurement over 10 Gbit or RDMA would give a different answer; nothing here says tensor parallelism across machines is a bad idea in general, only that this link is too slow for it.
