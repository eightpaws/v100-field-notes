# V100-91 - Recheck sm70-attn with head_dim 256

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** An earlier card (V100-30) rejected `sm70-attn` on the grounds that we had no model with
`head_dim 256`. That changed: upstream merged a comparable FA configuration for sm_70 (llama.cpp #27997), and
27B models with head dimension 256 had already been timed on the V100. The fork also carries SplitKV3, q4_0 KV
and DFlash2. Does the fork beat our own build on prefill at 8k and 16k on the same model, at comparable quality?
If not, the rejection stands - this time with numbers.

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute 7.0, driver 580.178.04 |
| Toolkit | CUDA 12.9 (nvcc 12.9) |
| Engine (fork) | `fishlikeX/sm70-attn`, HEAD `5e11845`, built for sm_70 |
| Engine (ours) | llama.cpp `dbaf582`, build 400 |
| Model | Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf, 11.77 GB, 3.4 bpw, 26.9 B parameters |
| Benchmark | `llama-bench`, `-p 8192,16384 -n 64 -ub 2048 -r 1`, `-fa on`, q4_0 KV |

**Commands.** Verbatim, fork path:

```
LLAMA_SM70_D256=1 LLAMA_SM70_D256_DECODE=1 LLAMA_SM70_D256_DEC_Q4=1 \
  llama-bench -m Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf \
  -p 8192,16384 -n 64 -ngl 99 -fa on -ctk q4_0 -ctv q4_0 -ub 2048 -r 1
```

The stock path is the same line with `LLAMA_SM70_D256=0`, so the kernel contribution is isolated with one
binary. Our own build runs the same flags with its own `llama-bench`.

**Repeats.** Single run, `n=1` per configuration.

**Result.** Prefill, tokens per second:

| Context | Fork `sm70-attn` 5e11845 | Our build dbaf582 | Delta |
|---|---|---|---|
| 8k | **1279.4** | 1178.9 | +8.5 % |
| 16k | **1224.6** | 1100.9 | +11.2 % |

Decode is identical within noise: 35.9 against 36.3 tok/s. The kernel alone, same binary with
`LLAMA_SM70_D256` on and off, is worth less than the whole fork: +4.2 % at 8k and +8.6 % at 16k.

**Verdict.** Positive for the narrow claim: the fork is faster on prefill at both measured lengths, and the
margin at 16k (+11.2 %) is large enough to matter for long prompts. The numbers published in the fork's README
(+34-48 %) do not reproduce at 8-16k: they belong to the 100-174k range, where the D256 kernel has much more
work per launch. Quality was not measured, so this is a speed result only.

**Result type.** Positive.

**Does not show.** Quality: no perplexity, no task benchmark, nothing that would tell whether the faster path
computes the same thing. No repeats - `n=1`, so the noise of these numbers is unknown. The comparison at 16k is
only possible with q4_0 KV: with f16 KV both engines run out of memory at 16k on a 16 GB card, so a
like-for-like f16 comparison at that length does not exist. SplitKV3 and DFlash2 from the same fork were not
exercised. All numbers are `llama-bench` prefill, not end-to-end server throughput with real prompts.

**Raw.** [`raw/runs/V100-91.json`](../raw/runs/V100-91.json) - both benchmark series, including the `[sm70-d256]`
kernel accept/reject lines from the fork's own tracing.
