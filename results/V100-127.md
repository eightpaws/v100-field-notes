# V100-127 - Multi-file edits that keep the public API intact

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Order work rarely starts from a blank file: it starts in someone else's project. A local coder
model has to change several files at once, keep every public signature callable exactly as before, and leave the
existing test suite green. Ten such tasks on a small but realistic package answer two things: can a 7B model
edit 2-4 files per task, and does a mechanical API gate catch what it breaks.

**Environment.**

| Model | Qwen2.5-Coder-7B-Instruct Q8_0, 8.1 GB GGUF |
| Engine | llama.cpp 1.0.0-dev, build 1224, commit 51831d47 |

VRAM used by the server at 16384 context, same flags, idle GPU: 9387 MiB.

**Commands.** Verbatim:

```
/root/bin/v100-run.sh V100-127 -- /root/venvs/app/bin/python /root/v127/run_v127.py
```

The script starts the server itself:

```
/root/llama-old/build/bin/llama-server \
  -m /srv/media/ai-cache/downloads/qwen7b-quants/qwen2.5-coder-7b-instruct-q8_0.gguf \
  -c 16384 -ngl 99 --host 127.0.0.1 --port 18427 -t 8 --jinja -fa 0
```

Each task is one `/v1/chat/completions` request: the whole project is pasted into the prompt, the answer must
come back as `### FILE: <path>` blocks with full file contents, and only paths under `shopcore/` are accepted.

**Reference project and tasks.** `shopcore` - five modules (`models`, `pricing`, `storage`, `cart`, `api`),
about 200 lines, typing and docstrings, ten pytest tests. The ten tasks, each naming 2-4 files: extract rounding
into `shopcore/rounding.py`; add a `currency` keyword; check stock at checkout; add a per-product discount field;
add `created_at` to the order; move constants to `shopcore/config.py`; add logging; add `Cart.clear()` plus
`checkout_and_clear`; add `Storage.remove_product` and `api.cancel_order`; delegate the discounted subtotal
through `Cart.total_with`.

**Gates.** Two, both mechanical:

1. *API compatibility.* A snapshot of every public function and class method via `inspect.signature`, taken on
   the pristine project and on the edited copy. A baseline callable must still exist with the same parameter
   names, order and defaults; a new parameter is allowed only when it carries a default.
2. *Tests.* The unchanged baseline suite must stay green (`pytest -q tests`).

**Result.** No. 7 of 10 edits pass both gates; the stated criterion was 8 of 10.

| Task | Files written | Generation | API gate | Tests | Pass |
|---|---|---|---|---|---|
| t01 rounding module | 4 | 10.1 s | ok | red (5 failed) | no |
| t02 currency argument | 3 | 9.1 s | ok | red (2 failed) | no |
| t03 stock check | 2 | 5.9 s | ok | green | yes |
| t04 product discount | 4 | 10.6 s | no | green | no |
| t05 created_at field | 3 | 7.6 s | ok | green | yes |
| t06 config constants | 4 | 9.3 s | ok | green | yes |

Generation is 5.9-10.6 s per task and 462-830 completion tokens per answer; the whole ten-task run took 87 s
wall clock, model load included.

The three failures are three different mistakes, which is the useful part:

* **t01 - wrong unit.** `round_cents` was implemented as `int(value * 100)`, i.e. the model decided the money
  values were rubles, not cents. Every total came back one hundred times too large and five tests went red.
  The API gate saw nothing wrong: names and signatures were intact.
* **t02 - wrong return type.** `with_tax` and `Cart.subtotal` were changed to return
  `{'total': 1200, 'currency': 'RUB'}`. The signature gate passes (parameters are unchanged), only the test
  suite caught it.
* **t04 - shifted positional arguments.** `discount_percent: int = 0` was inserted before `stock` in the
  `Product` dataclass, so `Product(1, 'tulip', 1000, 10)` now reads as a 10 percent discount with zero stock.
  Tests still pass because they use keyword arguments; the API gate caught the field order.

**Repeats.** Single run: one generation per task, ten tasks, no repeats and no resampling. The figure reported
is the fraction of edits passing both gates, not a speed, so no spread is quoted.

**Result type.** Negative.

**Does not show.** One model and one project of about 200 lines: a real repository with deep call graphs, imports
across packages and a slow suite is not represented. The type-contract gate is missing entirely - t02 shows that
a return type can change while the signature stays legal, so an acceptance harness needs type checking or
behavioural tests, not just `inspect.signature`. The tasks were written by the same person who wrote the project,
which makes the instructions cleaner than a client brief. There is no feedback loop: the model never sees the
test output, and "run the tests, hand the failures back" was not measured. Whether the model edits unrelated
files was judged only by counting written blocks, not by diffing line ranges.

**Raw.** [`raw/runs/V100-127.json`](../raw/runs/V100-127.json) - per-task file lists, generation seconds,
completion tokens, both gate verdicts and the failure notes. Run log: `/root/runs/V100-127/run.log` on the test
rig; edited copies kept in `/root/v127/work/t01..t10`.

**Verdict.** A 7B coder handles a multi-file edit about seven times out of ten, and the failures are not random:
one wrong unit, one changed return type, one inserted dataclass field. Signatures stayed compatible in 9 of 10
cases, so the API gate alone is not an acceptance test - it has to be paired with a green suite, and even then
a positional-argument shift in a dataclass is caught only by the signature snapshot.
