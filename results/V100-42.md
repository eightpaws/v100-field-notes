# V100-42 — MoE experts in system RAM: -ncmoe on V100 16 GB

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Can llama.cpp keep MoE expert weights in the 94 GiB of system RAM while attention and router stay on the GPU, so a model larger than VRAM still decodes at a useful speed?

**Environment.**

| Component | Version |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2 16 GB / 580.178.04 / 7.0 |
| Engine | llama.cpp master 51831d4 (built from source) |
| Runtime | CUDA 12.9.41, GCC 13 host compiler |
| Host | Proxmox VM, 24 vCPU, 94 GiB RAM, Ubuntu 24.04 |
| Model storage | ZFS pool over NFS (4.6 TB free) |

**Commands.**

```bash
llama-bench -m qwen3-coder-30b-a3b-q4_k_m.gguf -p 128 -n 32 -ngl 99 -ncmoe N -fa 0 -r 1
```

**Results.**

| Experts on CPU | prefill tok/s | decode tok/s |
|---|---|---|
| 4–6 | OOM (model does not load) | — |
| 8 | 411.9 | 75.5 |
| 12 | 298.7 | 63.3 |
| 16 | 247.6 | 58.8 |
| 24 | 181.2 | 45.7 |
| 32 (32k ctx, q8_0 KV) | 39.5 | 25.2 |

**Repeats.** single run per configuration

**Verdict.** Yes: 8 expert layers on CPU is the entry threshold, and every extra layer costs both prefill and decode roughly linearly. At 8 layers a 17.3 GB model — 1.3 GB larger than the card — decodes at 75 tok/s, against 3 tok/s for a dense 32B on the same card.

**Result type.** Positive.

**Does not show.** Only one model family was tested. The threshold depends on expert size, so 8 is not universal for other MoE architectures.

**Raw.** Not archived: no file for this run exists, so these numbers cannot be re-checked from the repository. Re-measurement is queued as V100-42b.

## Re-measurement (24.11.2026, commit af5c583)

The first series above was taken with the card shared with background services. After a server reboot the SDXL service (`imgd.service`, ~6.9 GB), `music-studio` and `ollama` came back on their own, and the same flags gave 3.7 tok/s — which looked like a build regression. It was not: the card was busy. With all three stopped and `0 MiB` confirmed before each run:

| n_cpu_moe | prefill pp256, tok/s | decode tg64, tok/s |
|---|---|---|
| 8 | 702.0 ± 25.4 | **51.0 ± 4.6** |
| 12 | 557.4 ± 3.0 | 50.7 ± 2.4 |
| 16 | 458.0 ± 16.1 | 38.1 ± 1.0 |
| 24 | 343.6 ± 4.3 | 29.8 ± 0.5 |

**Repeats.** 3 per configuration.

The spread between series (76.5 / 69.2 / 51.0 for the same flag) is host load, not the build: the services start with the machine and take up to 7 GB of the card.

Keeping every expert tensor in system RAM instead of offloading whole layers (`-ot "exps=CPU"`) is far worse: prefill 154.8 tok/s, decode **0.48 tok/s**.

**Practical rule.** Stop `imgd`, `music-studio` and `ollama`, verify zero used memory, and only then measure. Prefill drops linearly with the number of offloaded layers; decode holds up to 12 layers and decays after that. For a 30B MoE on 16 GB the working point is `-ncmoe 8`.
