# V100-125 - WordPress and WooCommerce: plugin edit with tests

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** A shop order is a plugin edit in someone else's code: add a free-shipping threshold by product
category to an mu-plugin and prove it with tests. Can a local coder model do that edit and pass a PHPUnit
suite on the first attempt, and does the choice of model matter at all when the specification is precise?

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute 7.0, 16 GB, driver 580.178.04 |
| Engine | llama.cpp 1.0.0-dev, build 1, commit b1b770d, CUDA 12.9 for sm_70, `llama-cli` |
| Models | Qwen2.5-Coder-14B-Instruct Q4_K_M (9.0 GB); DeepSeek-Coder-V2-Lite-Instruct 16B Q4_K_M; Qwen3-Coder-30B-A3B-Instruct Q4_K_M (18.5 GB, `-ncmoe 16`) |
| Runtime | PHP 8.3.6 (php8.3-mbstring, php8.3-xml), PHPUnit 11.5.58 from phar |
| Host | guest VM on a home Proxmox box, 24 vCPU, 94 GiB RAM |

**Commands.** Generation, verbatim per model:

```
/root/llama.cpp/build/bin/llama-cli \
  -m <gguf> -ngl 99 [-ncmoe 16] -c 4096 -n 700 --temp 0 --seed 42 -st \
  -f /root/v125/prompt.txt
```

The driver script `/root/v125/run.sh` (task 1) or `run2.sh` / `run3.sh` (task 1 per model, task 2) was started
through `/root/bin/v100-run.sh V100-125 -- /bin/bash <script>`. Extraction and scoring, verbatim:

```
python3 /root/v125/extract.py /root/v125/gen_raw_<tag>.txt /root/v125/gen_<tag>.php
IMPL=/root/v125/gen_<tag>.php php /root/phpunit.phar --do-not-cache-result /root/v125/v125Test.php
```

Task 1 asked for two global functions: `bf_category_totals()` (per-category sums, `round($sum, 2)`, `ksort`)
and `bf_free_shipping_eligible()` (per-category threshold, `default` for unlisted categories, true only when
every category sum is at or above its threshold). Task 2 added `bf_apply_free_shipping()`, which rewrites a
WooCommerce-style rates array (`cost` 0.0, label suffix ` (free)`) when the cart qualifies, and returns the
array untouched otherwise.

**Repeats.** Single run per model and task, temperature 0, seed 42. Generation time includes loading the
model from page cache, so it is not pure decode: the 30B figure carries an 18.5 GB read from a spinning pool.
Variance was not measured.

**Result.** All three models passed both suites on the first attempt, with no retries and no manual fixes:
Qwen2.5-Coder-14B Q4_K_M scored 10/10 and 6/6 in 7 and 8 seconds at a 9565 MiB VRAM peak;
DeepSeek-Coder-V2-Lite 16B Q4_K_M scored 10/10 and 6/6 in 6 and 6 seconds at 11481 MiB;
Qwen3-Coder-30B-A3B Q4_K_M with `-ncmoe 16` scored 10/10 and 6/6 in 16 and 20 seconds at 12909 MiB.
All six generations are syntactically valid PHP (`php -l` clean) and pass every test on the first attempt,
with no retries and no manual fixes. Both harnesses were validated against a hand-written reference
implementation before any model ran: 10/10 and 6/6, 14 and 10 assertions. The 30B model needed `-ncmoe 16`
to fit the card, the other two loaded fully with `-ngl 99`.

The interesting part is what did not happen: no model produced the classic `array_key_exists` versus `??`
mistake on a null threshold, none summed by string concatenation, none forgot `ksort`. On a specification
this precise the three models are interchangeable in quality, and the difference is only price: 9.6 GB and
7 s against 12.9 GB and 16 s for the 30B.

**Result type.** Mixed.

**Does not show.** No live WordPress or WooCommerce was loaded: the guest has no MySQL and no WP-CLI, the
test shop was not touched, so "does not break existing hooks" is untested - only pure functions were
exercised, without `add_filter`, `WC()->cart` or the shipping-rate objects WooCommerce really passes.
That missing piece is exactly where integration bugs live, so the 10/10 must not be read as "the plugin
works in the shop". One task family only, six test cases on task 2 and ten on task 1, all derived from the
same specification, so the suite measures spec-following rather than robustness. Single run per model; the
timings include model load and are not decode-throughput figures.

**Raw.** [`raw/runs/V100-125.json`](../raw/runs/V100-125.json) - per-run task, passed and failed test names,
generation seconds and VRAM peak. Generation logs: `run.log` of run `V100-125`.

**Verdict.** Yes for the edit itself, not for the integration: all three local coders wrote both functions
correctly on the first attempt (10/10 and 6/6, no fixes), so a 14B Q4 at 9.6 GB and 7 s covers this class
of work and the 30B buys nothing in quality. What the experiment cannot promise is the part the shop cares
about - that the hooks still behave with a real cart - because no WordPress runtime was involved.
