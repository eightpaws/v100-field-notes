# V100-84 — QWEN38-MTP flags from the recipe

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** In Qwen3.8-27B GGUF, MTP-head is already integrated, and the recipe `qwen38-mtp` provides a +33–39% boost in decoding with a single flag combination; there's a row for 2×V100-SXM2 in the authors' table. For us, MTP only gave a +21% boost on the "7B + 0.5B-draft" pair (V100-50), but the model head itself can work cheaper.

**Environment.** llama.cpp build129 (commit af5c583, CUDA 12.9), `llama-server`, Tesla V100-SXM2-16GB, driver 580.178.04; flags `-ngl 99 -c 4096 -fa 0 -t 8`, second run with `--spec-type draft-mtp`; VRAM 0 MiB at start.

**Repeats.** Single run (both configurations failed on model loading, no dispersion by definition).

**Result.** The MTP flag is present in the build (`--spec-type draft-mtp` in build129), but there's nothing to test it on: the only Qwen3.8-27B on disk is a third-party quantum `pxqn-onecard` (13.57 GB), its tensor type 263 is outside the list of llama.cpp (0..44), and the engine fails to load in 0.33s (`failed to read tensor info`, rc=1) before flag parsing even begins. Both base and MTP configurations died the same way. There's no native GGUF for this model; Qwen3.8-Flash-Next is only available in Strata shards (IQ1_M 58 GB, UD-IQ4_XS 93.7 GB), which can't be loaded in one pass on a 16 GB card. The claimed +33-39% decode boost on our card remains untested: there's no artifact that the engine accepts.
