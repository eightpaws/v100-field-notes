# V100-77 - Raon-1-nano MTP: multi-token prediction without a draft model

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04, ik_llama.cpp build129 (commit ac21694), CUDA 12.9, nvcc for sm_70._

**Environment.** Tesla V100-SXM2-16GB (sm_70), driver 580, CUDA 12.9, guest VM on a home Proxmox host; engine and model as recorded in the run log.

**Question.** The GGUF has a variant with an MTP (multi-token prediction) head, also 2.15 GB. If the engine can execute that head, speculative decoding works without a separate draft model — cheaper than the 7B + 0.5B scheme, where the gain was 21 %.

**Repeats.** n=3 for both files (llama-bench `-r 3`), mean ± stdev. Two independent series were taken on a clean card on 26.11.2026; both are listed below.

**Result type.** Negative - the MTP head brings no decode gain, so the plain file wins.

**Verdict.** The MTP head is dead weight in this engine: it loads but is never executed, no speculative counters appear in server responses, and decode never improves. Two clean-card series: 93.28 vs 92.72 tok/s and 90.75 vs 86.67 tok/s. The MTP file is at best equal to the plain one and at worst 4.5 % slower; use the plain Q4_K_M.

## Why the earlier figures differ

An earlier run reported 84.97 tok/s for the plain file and 63.54 for the MTP file, a 25 % penalty. That run happened while the RAG, coder and image services were resident on the card (about 8.8 GiB), so the MTP file, which loads the extra head, lost memory headroom. On an idle card the two files are equal. The clean measurement supersedes the earlier one; the difference is an artefact of contention, not a property of the model.

## Baseline

The plain Q4_K_M file at 93.28 tok/s is the baseline here. On the same card DeepSeek-Coder-V2-Lite reaches 183 tok/s and Nemotron-Bolt-E4B 113 tok/s, so this 1-nano model is not competitive for production decode regardless of the MTP question.

## What these numbers do not prove

- That MTP can never help: support may land later in llama.cpp or ik_llama.cpp; the weights are already on disk.
- That the head is architecturally inert: only the absence of speculative counters was observed, the implementation was not read.
- Quality: MBPP was not run on either file, and with MTP not executing there is nothing to compare.

## Next check

Re-open this card when upstream executes the MTP head, and verify the presence of `draft_n` / `draft_n_accepted` counters in a server response as the acceptance test.

Server logs of the pair stayed on the rig as `/root/runs/v77-server-{PLAIN,MTP}.log`.

**Result.** The MTP file loads on ik_llama.cpp (build ac21694) but the head is never executed: decode stays at or below the plain file (93.28 vs 92.72 and 90.75 vs 86.67 tok/s, n=3 each), and no `draft_n` / `draft_n_accepted` counters appear in server responses. Mainline llama.cpp 1.0.0-dev (af5c583) does not load the architecture at all: `unknown model architecture: 'raon1nano'`.

**Does not show.** Quality: no code benchmark ran on either file, and with the head idle there is nothing to compare. Whether a draft path can pay off on sm_70 at all (no tensor cores for it) remains open, so the negative verdict is about this engine, not about the architecture.
