# V100-124 — Third-party API integration: retries, timeouts, idempotency

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Orders often say "wrap this REST API": retries with backoff, timeouts, 429 and 5xx handling, idempotent replays, logging. Can a 7B coder model produce such a client from a written specification, and does it survive a server that actually misbehaves? The card sets the bar at 8 of 10 scenarios, with missing retries an automatic fail.

**Environment.** llama.cpp build129 (af5c583), Qwen2.5-Coder-7B-Instruct Q8_0 (7.1 GB), `-c 8192 -ngl 99 -t 8 --jinja --no-webui --seed 42`, temperature 0, one fresh `llama-server` process per run; GPU Tesla V100 16 GB sm_70, driver 580; guest on a home Proxmox stand, Python 3.12.

**Commands.**
```
/root/bin/v100-run.sh V100-124 -- /usr/bin/python3 -u /root/gen124.py
POST /v1/chat/completions {"max_tokens": 2200, "temperature": 0.0, "seed": 42}
python3 /root/api124.py /root/runs/V100-124/run_01/api_client.py
```
The mock server is stdlib `ThreadingHTTPServer` (a FastAPI mock was not needed: the same failure modes are two dozen lines of a handler). It serves `/ok`, `/flaky429` (two 429 with `Retry-After: 1`, then 200), `/flaky500` (two 500, then 200), `/always500`, `/drop` (closes the socket on the first call), `/slow` (sleeps 2 s), `/notfound`, and `POST /create` (500 on the first call, records `Idempotency-Key`). Ten scenarios: 200 path, 429 retry, 500 retry, retry exhaustion, dropped connection, timeout, idempotency key present, key reused across retries, `Retry-After` honoured, and no retry on 404. The harness itself was validated first: a reference client written by hand scores 10/10.

**Results.** Both runs produced byte-identical files (50 lines, sha 486f1d02, 413 completion tokens, 5.0 s), so repeatability is total. Scenarios passed: 3 of 10 in both runs — the bar of 8 is not met. All failures share one root cause: the parameter named `json` in `post()` and `_request()` shadows the `json` module, so `json.loads()` raises `AttributeError: 'NoneType' object has no attribute 'loads'` and even the `except json.JSONDecodeError` clause cannot be evaluated. The retry mechanics that did run are correct: exhaustion gives three requests, 404 is not retried, the timeout fires in 2.6 s. Idempotency is untested by construction — POST crashes before sending, so no `Idempotency-Key` header ever leaves the client.

**Verdict.** Negative: 3 of 10 scenarios in both runs. The retry skeleton is sound, but one shadowed name kills every request the client makes — exactly the class of defect that a test suite finds and a code review often misses.

**Result type.** Negative.

**Does not show.** One specification, one model, one quant. The parameter name `json` follows the `requests` API and is itself a trap: an implementation must import the module under another name (or rename the parameter). The measured 3/10 therefore mixes a model defect with a specification hazard, and the card does not separate them. Only one generated client was inspected; 429/5xx paths beyond the mock's modes and real network conditions were not tested. Generation time is warm-cache, not cold start.
