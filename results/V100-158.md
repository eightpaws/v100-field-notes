# V100-158 — Abliteration and code quality: two builds of one model at the same size and quant

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-131 compared coding of a 7B Q4_K_M against a 27B IQ3_S, so size and quantization changed together with the abliteration and the "coding loss" was never measured on its own. If abliteration leaves useful ability untouched, two builds of the same model at the same size and the same quant give the same pass@1 within noise; if it does not, they differ by more than 5 p.p.

**Environment.** llama.cpp `llama-server` at commit 51831d47, CUDA 12.9, driver 580.178.04, Tesla V100-SXM2-16GB, compute capability 7.0, Ubuntu 24.04, 24 vCPU, 94 GiB RAM; server flags `-ngl 999 -c 4096 -np 1 --jinja`; model load 37 s (base build) and 28 s (abliterated), VRAM 11,747 MiB after load, peak 11,963 MiB.

Models: `Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf` 11,771,546,784 bytes against `Huihui-Qwen3.8-27B-abliterated-GSQ-RCO-IQ3_S.gguf` 11,771,546,208 bytes — same quant type, same size to within 0.0005 percent.

**Commands.** `bash /root/bin/v100-run.sh V100-158 -- bash /root/bin/v100_158_driver.sh`; inside, for each build: `llama-server -m <gguf> --host 127.0.0.1 --port 18351|18352 -ngl 999 -c 4096 -np 1 --jinja`, then `python3 /root/code_eval.py --base-url http://127.0.0.1:<port> --model <gguf> --tasks 40 --max-tokens 1024 --no-think --temperature 0 --out <json>`, then `python3 /root/refusal_eval2.py --base-url http://127.0.0.1:<port> --model <gguf> --max-tokens 400 --out <json>`.

**Artifacts.** /root/runs/V100-158/run.log; JSON /srv/media/night/v100_158_plain_mbpp.json, v100_158_abl_mbpp.json, v100_158_plain_refusal.json, v100_158_abl_refusal.json; server logs /srv/media/night/v100_158_plain_srv.log, v100_158_abl_srv.log.

**Repeats.** Single run per build, 40 MBPP tasks, temperature 0. The base build produced exactly the same 25/40 as an earlier overnight run of the same file on a different engine build, so greedy decoding reproduces across builds and the two-task gap is a difference between the weights, not run-to-run noise.

**Result.** Abliteration did not cost coding quality and did remove refusals. The base build passed 25 of 40 MBPP tasks (pass@1 0.625) at 32.2 tok/s, the abliterated build of identical size and quant passed 27 of 40 (0.675) at 33.1 tok/s, and the solved set is a strict subset relation: 25 tasks solved by both, 13 failed by both, 24 and 27 solved only by the abliterated build. On 20 harmful-request prompts the base build refused 2 times, the abliterated build refused none, while categories A and C produced identical counts on both builds (7 of 7 and 4 of 4). Both builds took 13.5 minutes together, including 37 s and 28 s of model load; no task hit the 1024-token cap (maximum 877), so no answer was cut short.

**Does not show.** Forty tasks make one task worth 2.5 p.p., and the two-task difference is exactly 5.0 p.p., which sits on the boundary of this card's own criterion: this measurement supports "abliteration is not worse", not "abliteration improves code". The refusal set has 20 prompts in three categories and separates "refuses" from "answers at all"; it does not grade usefulness or safety of the answers given, and the categories and prompts are not published here. Only one engine commit was measured. Throughput is end-to-end through the HTTP server and includes prompt processing, not raw decode. The abliterated build generated 68 percent more tokens for the same 40 tasks (7,347 against 4,383) at the same tok/s, which is why its wall time per task is higher; why it writes longer answers was not investigated.

**Result type.** Positive

**Verdict.** Same model, same size, same quant: the abliterated build kept every task the base build solved and added two, while refusals on harmful prompts fell from 2 of 20 to zero.
