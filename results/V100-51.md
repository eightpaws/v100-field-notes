# V100-51 — 32k context for a 30B MoE on 16 GB

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Long files need a long context. Which combination of experts on CPU and KV compression keeps a 32k window alive on this card?

**Environment.**

| Component | Version |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2 16 GB / 580.178.04 / 7.0 |
| Engine | llama.cpp master 51831d4 (built from source) |
| Runtime | CUDA 12.9.41, GCC 13 host compiler |
| Host | Proxmox VM, 24 vCPU, 94 GiB RAM, Ubuntu 24.04 |
| Model storage | ZFS pool over NFS (4.6 TB free) |

**Commands.**

```bash
llama-cli -m qwen3-coder-30b-a3b-q4_k_m.gguf -ngl 99 -ncmoe N -c 32768 \
  -ctk q8_0 -ctv q8_0 -n 8 -p "test"
```

**Results.**

| KV | Experts on CPU | prompt tok/s | generation tok/s |
|---|---|---|---|
| f16 | 24 | 50.8 | 16.6 |
| f16 | 32 | 27.9 | 9.5 |
| q8_0 | 16 | 39.5 | **25.2** |
| q8_0 | 20 | 46.2 | 4.9 |

**Repeats.** single run per configuration (8 generated tokens each)

**Verdict.** 32k is reachable only with compressed KV plus offloaded experts: `-c 32768 -ctk q8_0 -ctv q8_0 -ncmoe 16` gives 25 tok/s. Without compression the same window needs 24+ CPU layers and drops to 16 tok/s.

**Result type.** Mixed.

**Does not show.** Measurements are single-run and noisy (the 4.9 tok/s outlier at 20 layers is unexplained, likely swap). No long-prompt accuracy check beyond the context actually being processed.
