# V100-155 — PXA 27B: Quality on 8k context

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** The V100-150 reduced speed by 8k, but quality was measured only at 4k (V100-148, 0.600); on long context, PXQN may degrade more than usual Q4.

**Environment.** PXA 4.0.4 (`pxa-launch --engine llama` from unpacked OCI image), model poisonxa/Qwen3.8-27B-PXQN-OneCard 12,625 GiB (3,969 BPW); `-c 16384 --np 2`, i.e., 8192 contexts per slot; Tesla V100-SXM2-16GB, sm_70, driver 580.178.04, CUDA 12.9; Ubuntu 24.04.5, 24 vCPU, 94 GiB RAM

**Commands.** `$DIST/pxa-launch -m /srv/media/ai-cache/downloads/qwen38-27b-pxqn-onecard.gguf --engine llama -c 16384 --np 2 --port 18097 --no-tui --no-interactive --yes`, then `python3 /root/v155_eval.py --base-url http://127.0.0.1:18097 --model <id from /v1/models> --tasks 40 --pad-tokens 0|6000|7400` (third run with 7400 to reach actual prompt of 5948 tokens); run both sessions - `bash /root/bin/v100-run.sh V100-155 -- /root/v155_driver.sh` and `-- /root/v155_driver6k.sh`

**Results.**

| Prompt | Average Tokens in Prompt | MBPP pass@1 | Passed | Time per Task (s) | Throughput (tok/s) |
|---|---|---|---|---|---|
| Short | 57 | 0.575 | 23/40 | 1.58 | 69.6 |
| Padded | 4,863 | 0.575 | 23/40 | 2.45 | 49.1 |
| Padded to 6k | 5,948 | 0.575 | 23/40 | 3.56 | 38.1 |

**Artifacts.** /root/runs/V100-155/run.log; JSON /srv/media/night/v100_155_short.json, v100_155_long.json, v100_155_long6k.json; server logs /srv/media/night/v100_155_srv.log, v100_155_srv6k.log

**Repeats.** Each prompt length, run once with 40 MBPP tasks each; temperature 0, so no sampling.

**Result.** The quality on long prompts did not drop: MBPP pass@1 **0.575 (23/40)** and on short prompts (57 tokens), and when padded to 4,863 and to **5,948 tokens** - exactly 23 out of 40 in all three measurements, criterion 0.55 met. The answers change: the code differs for 30 tasks out of 40, but success or failure switches only for two (task 1 and task 36), and both times in opposite directions, so the set of passed remains the same. The cost of context is visible in speed: **69.6 tok/s** on short prompt, 49.1 on 4.9k, and **38.1 tok/s** on 5.9k - increasing the prompt by a hundred times costs 1.8× throughput. The peak VRAM **15,549 MiB** is the same for all lengths: KV cache is calculated for the entire 16,384-context at `-np 2`, not for the actual prompt.

**Does not show.** The prompt was inflated with neutral text, not a real long file: context length was measured, not material complexity, and finding a needle in a haystack was not tested by this measurement. No control point was set on another engine (llama.cpp Q4_K_M), so the contribution of context is not separated from the properties of the checkpoint - but the quality did not change at all, so there is nothing to separate. The difference from 24/40 in V100-148 is one task, that is, noise of one pass.

**Result type.** Positive

**Verdict.** Long context costs speed, not accuracy here: pass@1 held at 0.575 from a 57-token prompt to 5,948 tokens, while end-to-end throughput fell 1.8x.
