# V100-26 — llama.cpp build flags matrix for Volta

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** V100-oriented builds set non-default flags: `-DGGML_CUDA_FORCE_MMQ=OFF -DGGML_CUDA_F16=ON -DGGML_CUDA_FORCE_CUBLAS=ON`, plus `GGML_CUDA_FA_ALL_QUANTS=ON`. Our binaries and packages are built by default, so part of the performance gain may simply lie in the flags.

**Result.** The build flag matrix was previously verified (CUDA 12.0, llama.cpp build b7743fbfd8, model 14B Q4_K, llama-bench pp512/tg128, median of three runs). Result: none of the flags recommended for V100-oriented builds provide a noticeable improvement. | Configuration | What was observed | |---|---| | base | baseline | | `-DGGML_CUDA_FORCE_MMQ=OFF -DGGML_CUDA_F16=ON` | build did not improve `llama-bench`, discarded | | `-DGGML_CUDA_F16=ON` separately | less than 1% | | `-DGGML_CUDA_FORCE_CUBLAS=ON` | less than 1% | | `-DGGML_CUDA_FA_ALL_QUANTS=ON` | less than 1% | | all at once | less than 1% | The entire performance gain on our map comes from the volta-fa patches in the code itself (see V100-16: +7.4% decode against Ollama), and this is already accounted for in the working build. Note: measurements were taken with an old toolset (CUDA 12.0). After switching to CUDA 12.9 and master llama.cpp, flags may formally behave differently, but their mechanism remains the same - selection of kernels for matrix multiplications - so there is no need to recheck the entire set for 10 minutes per configuration. If necessary, it is faster to check the `GGML_CUDA_F16` flag on the current build.
