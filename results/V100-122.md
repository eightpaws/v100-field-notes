# V100-122 — Output stability: five repeats of one task

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** A client order is quoted by one generation, but delivered code has to come out right every time. Does the same specification produce the same working module on repeated runs, and does a small temperature change break it? The card sets a shipping bar: at least 4 of 5 runs green on tests at temperature 0, at least 3 of 5 at temperature 0.2.

**Environment.** llama.cpp build129 (af5c583), Qwen2.5-Coder-7B-Instruct Q8_0 (7.1 GB), `-c 8192 -ngl 99 -t 8 --jinja --no-webui`, one fresh `llama-server` process per run (no shared prefix cache), GPU Tesla V100 16 GB sm_70, driver 580, guest on a home Proxmox stand, Python 3.12, pytest 9.2.0 in a separate venv.

**Commands.**
```
/root/bin/v100-run.sh V100-122 -- /usr/bin/python3 -u /root/stab122.py
llama-server -m qwen2.5-coder-7b-instruct-q8_0.gguf --port 1838N -ngl 99 -c 8192 --jinja --no-webui -t 8 --seed 42
POST /v1/chat/completions {"max_tokens": 2200, "temperature": 0.0}   # runs 1-5, seed 42
POST /v1/chat/completions {"max_tokens": 2200, "temperature": 0.2}   # runs 6-10, seed 1006..1010
python -m pytest -q test_taskqueue.py -p no:cacheprovider            # 12 hidden tests, same set for every run
```
The specification was one medium task: a `taskqueue.py` module on the standard library only — priority queue with FIFO tie-breaking, statuses pending/running/done/failed, retry counter, JSON storage loaded in the constructor, module-level `load()`, `ValueError('corrupt queue file')` on broken JSON, and an argparse CLI. The 12 acceptance tests were written from the specification before any run, not by the model.

Generation took 11.2 s per run at temperature 0 (925 completion tokens) and 7.6-11.5 s at 0.2 (627-952 tokens); VRAM stayed at 8.3 GB, no run hit an out-of-memory error. Repeatability at temperature 0 is absolute: five runs produced byte-for-byte the same file. At 0.2 the shape varies — five different files, 73 to 115 lines, a ±40% spread on the same specification.

Quality is the opposite story. Every one of the ten outputs passed exactly 4 of 12 tests, and always the same four: `add()` with the pending counter, `KeyError` on an unknown id, `ValueError` on broken JSON, and `next()` returning `None` on an empty queue. All ten files contain the same defect: `next()` calls `self.tasks.index(x)` while `self.tasks` is a dict, so it raises `AttributeError` — every path through the scheduler is dead. Loading in the constructor raises `TypeError`, so the CLI `stats` command cannot read a file it just wrote.

**Verdict.** Negative: 0 of 5 runs green at temperature 0 and 0 of 5 at 0.2, so the shipping bar is not met. Repeatability is not quality — temperature 0 reproduces the same defect with byte-exact fidelity, which is worse for a quoted order than a model that occasionally gets it right.

**Result type.** Negative.

**Does not show.** One specification and one model: the numbers say nothing about other tasks, other quants, or the 14B model. The 12 tests cover the written requirements only, not style, structure or performance. Temperatures above 0.2 were not measured. Generation time was taken with a warm page cache, so it is not a cold-start figure. The first series of this card was discarded: its specification left the pending filter and the `load()` signature ambiguous, so part of the failures belonged to the wording — that series stays on the stand at `/root/runs/V100-122-serie1` and is not used here.
