# V100-128 - Writing tests for someone else's code: coverage and defect detection

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** A module arrives without tests. Can a local 7B coder model write a suite that is both green on
the correct code and useful as a safety net? Coverage alone does not answer that: tests on getters can reach
80 % while catching nothing. The second number is the mutation score, measured on ten hand-made defects.

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute 7.0, 16 GB, driver 580.178.04 |
| Model | Qwen2.5-Coder-7B-Instruct Q8_0, 8.1 GB GGUF |
| Engine | llama.cpp 1.0.0-dev, build 1, commit b1b770d, built with CUDA 12.9 for sm_70 |
| Runtime | Python 3.12.3, pytest 9.2.0, coverage 7.17.5 |
| Host | guest VM on a home Proxmox box, 24 vCPU, 94 GiB RAM |

**Commands.** Generation, verbatim:

```
/root/llama.cpp/build/bin/llama-cli \
  -m /srv/media/ai-cache/downloads/qwen7b-quants/qwen2.5-coder-7b-instruct-q8_0.gguf \
  -f /root/v128/prompt.txt -n 3000 -c 8192 -ngl 99 -t 8 --temp 0.2 \
  -st --no-display-prompt --simple-io
```

The driver script `/root/v128/run_all.sh` was started through `/root/bin/v100-run.sh V100-128 -- ...`.
Scoring, verbatim: `python3 /root/v128/run_v128b.py /root/v128/gen_tests.py run1`.
`llama-server` is not built in this tree (`tools/ui` asset step fails), so generation used `llama-cli`
instead of the HTTP server.

**Repeats.** n=3 independent generations of 18 tests each, every run on an idle GPU.
Tests passing on the pristine module: 4 / 3 / 4 of 18. Coverage of passing tests: 22.8 / 22.2 / 22.8 %.
Planted defects caught: 1 / 1 / 1 of 10. Generation took 23.4 s including the model load, VRAM peak 8281 MiB.

**Result.** No. All three suites are red on the correct code: 14 of 18 tests fail. Counting only the tests
that are green on the pristine module, coverage is 22.2-22.8 % against a 60 % target, and 1 of 10 planted
defects is caught (the rounding substitution). The defects are of two kinds:
nine failures are `NameError` on `BillingError`/`CouponError` - the model writes `pytest.raises(...)` but never
imports the exceptions - and five are wrong expectations (progressive price tiers read as flat, a tax rate
taken as a percentage instead of a fraction, proration rounded differently, invoice totals that do not add up).
The harness itself was validated first: the reference suite catches all ten mutations, otherwise the score is
void. The first version of the score reported 83.6 % coverage and 10/10 mutations, which is an artefact - a
suite that is already red fails on every mutant, and coverage counts lines executed by failing tests too.

**Result type.** Negative.

**Does not show.** This is one module of 380 lines and one model; larger or more idiomatic code could behave
differently. No second model was tried, and no feedback loop (run the tests, hand the failures back) was
measured - the numbers describe a single shot. The ten mutations are hand-made and all lie inside function
bodies; missing validation, wrong API contracts or concurrency defects are not represented. Coverage of the
passing subset is a lower bound, because the failing tests still execute code that the passing ones do not.

**Raw.** [`raw/runs/V100-128.json`](../raw/runs/V100-128.json) - per-run totals, the names of passing and
failing tests, the list of caught and surviving mutations. Generation logs: `run.log` of runs `V100-128`,
`V100-128-gen2`, `V100-128-gen3`.

**Verdict.** A single-shot 7B coder writes tests that do not even run against the code it was given
(14 of 18 fail, mostly on missing exception imports), and the subset that is green covers 22 % and catches
1 of 10 defects. Acceptance gates must run the generated tests before they are trusted; asking for branch
coverage in the prompt does not fix a missing import.
