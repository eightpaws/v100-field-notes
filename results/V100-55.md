# V100-55 — There is no 20-layer limit: the ceiling is one device buffer of weights

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, Ubuntu 24.04, driver 580.178.04, CUDA 12.9._

**Question.** An earlier card reported that `llama-bench` refuses to load the model at `-ngl` 40 and 99 while its stderr was never captured. Is that a tool check, an OOM of the weight allocation, or a real limit on the number of offloaded layers — and where exactly does loading stop?

**Environment.** llama.cpp `1.1.0-dev`, build 1, commit `28148b5`, `llama-bench`; Tesla V100-SXM2-16GB, compute capability 7.0, 16144 MiB VRAM; driver 580.178.04, CUDA 12.9; Ubuntu 24.04, 24 vCPU, 94 GiB RAM. Models: Qwen2.5-32B-Instruct Q4 GGUF (64 layers, 19.85 GB on disk, `model_size` 19845357568), Qwen3-30B-A3B Q4 (17.28 GiB), Qwen2.5-7B-Instruct Q4 (5.1 GiB). KV cache f16, `n_batch` 2048, `n_ubatch` 512.

**Commands.** One configuration per invocation, stdout and stderr saved separately:

```
llama-bench -m /models/qwen2.5-32b-instruct.gguf -ngl <20|24|28|32|40|44|48|52|56|60|64|99> -p 128 -n 16 -r 1 -o json
llama-bench -m /models/qwen3-30b-a3b.gguf       -ngl 99 -ncmoe <8|16|24>                       -p 128 -n 16 -r 1 -o json
llama-bench -m /models/qwen2.5-7b-instruct.gguf -ngl 99                                        -p 128 -n 16 -r 1 -o json
llama-bench -m /models/qwen2.5-32b-instruct.gguf -ngl 48                                       -p 128 -n 16 -r 2 -o json
```

Peak VRAM was sampled concurrently with `nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits` every 0.2 s.

Control, 7B Q4 at `-ngl 99`: prefill 1359.0 tok/s, decode 120.0 tok/s.

The refusal is a single allocation, not a layer-count check. At `-ngl` 56 the loader asks for one 16636948480-byte buffer and gets `out of memory`; at `-ngl` 99 it asks for 19407413248 bytes:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 18508.35 MiB on device 0: cudaMalloc failed: out of memory
ggml_backend_buft_alloc_buffer_n_default: failed to allocate CUDA0 buffer of size 19407413248
llama_model_load: error loading model: unable to allocate CUDA0 buffer
llama_bench: error: failed to load model '/models/qwen2.5-32b-instruct.gguf'
```

**Repeats.** The layer ladder and the MoE matrix are single runs (`-r 1`). The repeated point is the ceiling config `-ngl 48`, n=2: prefill 127.2 ± 5.5 tok/s, decode 7.3 ± 0.4 tok/s. Configurations that fail to load were each run once.

**Result.** 52 of 64 layers load and run: prefill rises from 67.2 tok/s at 20 layers to 147.9 tok/s at 52 (x2.2), decode from 3.9 to 9.6 tok/s (x2.5), with peak VRAM 15659 of 16144 MiB (97 %). Loading stops between 52 and 56 layers, and the failure is one `cudaMalloc` of all offloaded weights (15.5-18.1 GiB) against a 16 GB card, so the boundary is set by VRAM, not by the layer count. On the 30B MoE with `-ngl 99`, moving experts to CPU gives 404.3 / 85.8 tok/s at `-ncmoe 8` and 192.4 / 47.7 at `-ncmoe 24`. The earlier figure of 20 layers came from runs at 8k context, where context buffers consume the same memory (V100-65).

**Result type.** Positive.

**Verdict.** There is no 20-layer limit: 52 of 64 layers fit and run, and the refusal above that is a single failed allocation of the whole offloaded weight buffer — which is also why `-ngl 99` cannot work on any model larger than 16 GB.

**Does not show.** One GGUF (32B Q4) at one context length (128 prompt tokens): at 8k context the boundary moves down because KV and compute buffers take the same VRAM. Peak VRAM was sampled only from `-ngl` 44 upward, so the 20-40 rows carry speed but not memory. One quant family only — Q8 or a 70B model shifts the ceiling by arithmetic. Nothing here says how much a real pipeline gains from the extra layers: that needs per-frame timing, not tok/s.
