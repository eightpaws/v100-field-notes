# V100-93 - Two-machine pipeline: V100 writes, 4060 Ti reviews

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580._

**Question.** A two-stage pipeline already worked in pieces: a writer at 132 tok/s on the V100, a reviewer
(mistral-nemo) on the 4060 Ti at 21.8 s per pair with zero false alarms. The end-to-end question was never
measured: if review runs while the next edit is being written, 20 tasks should close faster than doing both
stages on one card. The stated criterion: the split mode must be at least 15 % faster at the same acceptance
rate.

**Environment.**

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM2-16GB, compute 7.0, driver 580, CUDA 12.9 |
| Engine | llama.cpp build129, commit b5b3f5e, `system_fingerprint b1-af5c583` |
| Writer (mode a) | Qwen2.5-Coder-7B-Instruct Q8_0, `-ngl 99` |
| Writer (mode b) | Qwen2.5-Coder-7B-Instruct Q4_K_M, `-ngl 12` (8 layers on CPU to fit beside the reviewer) |
| Reviewer (mode b) | GLM-4.7-Flash 30B-A3B Q4_K, `-ngl 99 -ncmoe 20`, port 18450 |
| Runtime | Python 3.12 |

**Commands.** Verbatim:

```
bash /root/v93_run.sh          # mode (a): both stages on the V100
bash /root/v93_pipe_run.sh     # mode (b): writer + separate reviewer
```

Both wrapped in the run lease: `/root/bin/v100-run.sh V100-93 -- ...`. Harnesses: `/root/v93_seq.py`
(mode a) and `/root/v93_pipe.py` (mode b).

**Repeats.** Single run per mode, 20 tasks in each series, noise not measured.

**Result.** 20 tasks per mode, the same task set:

| Metric | (a) both stages on the V100 | (b) writer + separate reviewer |
|---|---|---|
| Total | **26.52 s** (1.33 s/task) | **108.47 s** (5.42 s/task) |
| Generation | 17.32 s | 78.02 s |
| Review | 9.18 s | 30.41 s |
| Mechanical gate | 20/20 | 20/20 |
| Accepted by reviewer | 17/20 (7B) | 19/20 (30B) |

**Verdict.** Negative for the criterion. The split mode is 4.1x slower, not 15 % faster, and the margin is far
outside any noise. The mechanism is visible in the numbers: the writer in mode (b) gave up 8 layers to the CPU
(`-ngl 12`, otherwise it does not fit beside a 30B reviewer), decode fell from ~9 to ~4 tok/s, and all 20 tasks
still queue on one card, so nothing runs in parallel. The reviewer quality gain is real but small (19/20 against
17/20, two false alarms of the 7B removed) and does not pay for 4x the time. The real gain needs the reviewer on
a second card.

**Result type.** Negative.

**Does not show.** The reviewer never ran on the 4060 Ti: the PC refused access during this run (no SSH key,
ports 11434 and 22 closed by firewall, no sshd installed, no admin rights in the session), so mode (b) is a
same-card comparison. The hypothesis "parallel review on a second GPU" therefore remains untested - what is
measured here is the cost of carrying two models on one card. Single run per mode, and the earlier 21.8 s per
pair on the 4060 Ti is a field number from another session, not re-measured here.

**Pitfalls that cost three runs.** GLM-4.7-Flash is a reasoning model: at `max_tokens=200` it spends the whole
budget thinking and returns empty `content`, so all 20 reviews came back "unparsable" and it reads as "the
reviewer rejected everything". Fixed with `max_tokens>=1200` plus `chat_template_kwargs.enable_thinking=false`.
The mechanical gate required `def <name>` at the top level of the AST only and rejected a correct decorator
factory; the check was moved to `ast.walk`. Other services on the guest (`ragllm.service`, `ollama`) start the
card on their own and are unknown to the cleanup script - the card was taken to 13 GB mid-run and the runner
refused with code 5, so both must be stopped before a series.
