# V100-21 — Tachyon, Ninfer, Lapilli

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Tachyon-v100 (Rust + native CUDA cores), ninfer-v100 and lapilli-v100 (ports with compat layer replacing cp.async/ldmatrix/bf16 with sm_70-equivalents) - prove that "rewriting for Volta" is feasible. The question is not about possibility, but whether they outperform patched llama.cpp on our card.

**Result.** Tachyon-v100 is being built and run on our card, but our models do not support it. Verified step by step. Build (Rust + nvcc), three pitfalls: 1. build.rs looks for the compiler strictly in `$CUDA_HOME/bin/nvcc`, but it's located in `/usr/lib/nvidia-cuda-toolkit/bin` on the system. Fixed with a wrapper directory: `mkdir -p ~/cuda-home/bin && ln -s /usr/lib/nvidia-cuda-toolkit/bin/nvcc ~/cuda-home/bin/nvcc`. 2. CUDA 12.0 does not understand gcc 13+ headers, spits out `_Float32 is undefined`. Need `-ccbin g++-12` (gcc-12 is in the system). 3. nvcc cannot find its own `cicc` if `/usr/lib/nvidia-cuda-toolkit/bin` is not in PATH. Final command that worked in 5 minutes 47 seconds and produced binaries `tachyon`, `tachyon-serve`, `ggufinfo` and a dozen utility tools: ``` export PATH=/usr/bin:/bin:/usr/lib/nvidia-cuda-toolkit/bin:$HOME/.cargo/bin export CUDA_HOME=$HOME/cuda-home export INFER_NVCC_FLAGS="-ccbin g++-12 -allow-unsupported-compiler" cargo build --release ``` Running on our models is blocked by architecture: the engine accepts only `qwen35`, `qwen35moe` and `sensenova_loop`. On `qwen2.5-7b-instruct.gguf` it crashes with `arch ... not qwen35`, on `qwen3-30b-a3b.gguf` - with `arch not qwen35, but qwen3moe`. So the engine is tailored for the Qwen3.8-27B line, which we don't have, and cannot be downloaded now: measurements gave 700 bytes/s download speed from HF. Conclusion: postpone until Qwen3.8 GGUF becomes available. Current value - working build recipe, it will be needed if weights appear.
