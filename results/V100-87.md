# V100-87 — marlin_v100: INT4 Marlin kernels on sm_70

<!-- curated: do not overwrite -->

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Does the dedicated Marlin INT4 workspace for SM70 (`zhinianqin/marlin_v100`) deliver a
decode speedup on Volta, and does it explain why AWQ/GPTQ paths on this card fall into the slow fallback?

**Results.** Build and import succeed: `_C.abi3.so` 509 MB, `_moe_C.abi3.so` 447 MB,
`torch.ops._C.marlin_gemm` is registered on sm_70. Numerics are correct: 12/12 dense cases `OK`,
`max_abs=0`, `MISMATCH=0`.

Timing is flat across the whole batch: every call takes 175-185 us regardless of M (K=512, N=256),
so the kernel is dominated by a fixed per-call cost rather than by arithmetic.

| M | Marlin INT4 us | Marlin TFLOP/s | torch fp16 cuBLAS us | fp16 TFLOP/s |
|---|---|---|---|---|
| 1 | 178.2 | 0.0015 | 17.4 | 0.02 |
| 512 | 184.3 | 0.91 | 18.3 | 7.33 |
| 4096 | 185.3 | 5.79 | 25.9 | 41.53 |
| 5120 | 184.3 | 7.28 | 27.5 | 48.84 |

Larger shapes behave the same way: at M=1, K=N=4096 the Marlin path needs 326.6 us where fp16 cuBLAS
needs 47.0 us; at M=32 the ratio is 338.6 vs 55.5 us.

**Verdict.** Negative for Volta: the Marlin INT4 path is 7-10x slower than plain fp16 GEMM on identical
shapes, at decode (M=1) the kernel spends 178 us where cuBLAS spends 17, so the "+20% decode" target is
not reachable through this workspace. The fixed, M-independent cost points at the Volta INT4 path itself:
no MMA-style tensor-core path and no `cp.async`, so each launch pays the same price as a large GEMM.

**Result type.** Negative.

**Does not show.** The measurement is kernel-level, not model-level: no vLLM server was started with real
GPTQ/AWQ weights, so end-to-end decode tok/s was never measured, and the criterion is refuted by the
kernel numbers rather than by a serving run. The dequant+matmul baseline emulated in Python is not a fair
reference (its constant 148 us is dominated by the emulation, not by llama.cpp). No MoE kernels were
benchmarked, the `_moe_C` extension was only verified to load. Single run per configuration, no repeats.
