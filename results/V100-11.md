# V100-11 — System-prompt KV cache: prefix reuse in llama-server vs Ollama

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** A chat agent and a shop assistant both open every conversation with the same 2–6k-token system
prompt. If the prefix cache survives between requests, that prefill is paid once instead of on every turn. How
much does each engine actually reuse — and does an edit at the tail of the prompt invalidate everything?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engines | llama.cpp `llama-server` (built from source for sm_70) vs Ollama 0.40.16 |
| Model | qwen2.5-7b-instruct, Q4 GGUF (`/models/qwen2.5-7b-instruct.gguf`) |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |
| Scenario | prefixes of ~2k and ~6k tokens; cold slot, repeat, tail edit |

**Commands** (verbatim from the run script):

```bash
/srv/media/ai-cache/llama-volta/llama.cpp/build/bin/llama-server \
  -m /models/qwen2.5-7b-instruct.gguf --port 8081 -c 8192 \
  -ngl 99 -fa on -np 1 --host 127.0.0.1
```

```python
# same script, both engines: read prompt_eval_duration from the API and convert to ms
payload = {"model": "qwen2.5:7b-instruct",
           "messages": [{"role": "system", "content": sys_prompt(2000)},
                        {"role": "user", "content": "Name three catalog rules."}],
           "stream": False, "keep_alive": "10m",
           "options": {"num_predict": 16, "temperature": 0}}
```

Three scenarios per prefix: cold slot, identical repeat, and an edit in the last user message.

**Results.** Prefill time, milliseconds (`prompt_tokens` in parentheses where the engine reports a partial prompt):

| prefix | engine | cold | repeat | tail edit | no cache |
|---|---|---|---|---|---|
| ~2k | llama-server | 1046.7 (1697) | 663.3 (13) | 95.2 (34) | 568.7 (1697) |
| ~6k | llama-server | 1106.1 (3368) | 186.2 (13) | 205.4 (34) | 1541.1 (5045) |
| ~2k | Ollama | 532.8 (1697) | 134.5 (1696) | full recompute | — |
| ~6k | Ollama | 967.4 (5045) | 198.7 (5044) | full recompute | — |

Wall time for the cold llama-server call at ~2k was 1.2 s; the Ollama cold call at ~2k was 12.4 s because the
model had to load.

**Repeats.** The first run died with `RemoteDisconnected` and is not in the table; the second run produced the
numbers above, one measurement per scenario (`n=1`).

**Verdict.** Enable the prefix cache in `llama-server` — it is the cheap win, and it is the only one of the two
that survives a tail edit (95 ms instead of re-prefilling 1697 tokens). Ollama reuses the prefix on a byte-identical
repeat but recomputes the whole prefix on any tail change. Either way, freeze the order of the system-prompt
fields: a date or a request counter at the top of the prompt invalidates the cache on every request.
