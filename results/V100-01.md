# V100-01 — Speculative decoding in llama.cpp

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** Decoding on V100 hits the limit at 900 GB/s: all weights are read for each token. If multiple candidate tokens are checked in one pass, memory reads become less frequent and time per token decreases. Expected results: 1.3–1.8× speedup for qwen2.5-coder-14b Q4 (66 → 85–120 tok/s), the gain is smaller for 7B - there it's already 105 tok/s.

**Environment.** llama.cpp, speculative decoding draft-simple; V100 16GB (sm_70), driver 580, CUDA 12.9

**Repeats.** single run

**Result.** Speculative decoding was tested on two targets, and the result depends on the model pair: it accelerates on 7B, but slows down almost twofold on 14B. llama.cpp master 51831d4, CUDA 12.9, server with `--spec-type draft-simple -md qwen2.5-0.5b-instruct-q8_0 --spec-draft-ngl 99 --spec-draft-n-max 8`, one slot, same prompt "explain briefly what prefix cache is", 96 tokens each: | Target | Without Draft | With Draft | |---|---|---| | Qwen2.5-Coder-7B | 111.5-114.2 tok/s | **134.6-140.3 tok/s (+21%)** | | Qwen2.5-Coder-14B | **67.0-67.6 tok/s** | 35.9-38.6 tok/s (**-43%**) | The reason is clear from physics: on 7B, one target token is cheap, and the 0.5B draft manages to generate 8 candidates that are accepted more often - there is a win. On 14B, candidate verification is more expensive, and fewer are accepted (the draft is weaker relative to the target), so on average more work is spent per token than without speculation. Practical conclusion: enable speculation only after measurement on a specific pair; the draft should be 10-20 times smaller than the target and from the same family (same tokenizer). Our ready candidate is only the 7B + 0.5B combo, which gives +21%. Pitfalls: `llama-cli` does not enable speculation (flag is accepted, speed does not change), `llama-server` with explicit `--spec-type` is needed; the type is called `draft-simple`; without `--spec-draft-ngl 99`, the draft remains on CPU and there is no gain.
