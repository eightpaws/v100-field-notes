# V100-79 — llama.cpp v1.0.0 vs our build 51831d4

_Measured on a Tesla V100-SXM2 16 GB (sm_70) inside a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Question.** The first stable tag of llama.cpp (13.11.2026) brought MoE-cache experts in RAM, FP8-KV and MTP to the public API, but Volta prefill regressed: in issue #32245 (8×V100) 1446 → 283 tok/s, in #32810 (Qwen3.8-27B on V100) 964 → 778 at 5k and 822 → 522 at 16k. Our build 51831d4 may perform better for agent sessions.

**Environment.** Tesla V100-SXM2-16GB (cc 7.0, 16 144 MiB) · driver 580.178.04 · CUDA 12.9.41 in `/home/hermes/cuda-12.9` · Ubuntu 24.04, EPYC 7282 (24 vCPU) · builds: `51831d47` (1224) and `v1.0.0 = b1b770d`, both through `~/bin/build-cuda.sh`, host-compiler gcc-12

**Commands.** `llama-bench -m <gguf> -ngl 99 -fa 0 -p 2048,8192,16384 -n 32 -r 1 -o md` - one per model and build (4 runs).

**Artifacts.** srv/media/night/v100_79/bench_{old51831d4,v100}_{qwen2.5-coder-7b-instruct,deepseek-coder-v2-lite}-q4_k_m.md; logs /root/runs/V100-79/run.log, run_step1.log; directories /root/llama-old and /root/llama.cpp.

**Repeats.** Single run per point (r=1). pp2048 on 7B old build taken twice: 3002.15 and 2980.75 - discrepancy 0.7%, small spread.

**Result.** Regression on sm_70 has occurred, but only for MoE. llama-bench, `-ngl 99 -fa 0 -r 1`, both builds on the same stand: | test | DeepSeek-V2-Lite 16B · 51831d4 | same · v1.0.0 | Qwen2.5-Coder-7B · 51831d4 | 7B · v1.0.0 | |---|---|---|---|---| | pp2048 | 3368.5 | **1968.7 (-41.6 %)** | 2980.8 | 3076.7 (+3.2 %) | | pp8192 | 2698.6 | **1668.4 (-38.2 %)** | 2282.8 | 2278.0 (-0.2 %) | | pp16384 | 1970.4 | **1348.2 (-31.6 %)** | 1631.4 | 1626.9 (-0.3 %) | | tg32 | 178.1 | 176.1 (-1.1 %) | 122.9 | 122.9 (0.0 %) | The dense 7B tag does not change anything (difference within 0.3 %, except pp2048 +3.2 %), for MoE `deepseek2` prefill drops by 32-42 % with the same decode. ## Independent confirmation (24.11.2026)

Second series on a different MoE family, idle card confirmed at 0 MiB before each run, `-r 3`, same flags (`-ngl 99 -fa off -p 256 -n 64`) for both builds:

| Model | Build | prefill pp256, tok/s | decode tg64, tok/s |
|---|---|---|---|
| Qwen2.5-Coder-7B Q4 (dense) | v1.0.0 | 2279.4 ± 85.0 | 124.0 ± 0.3 |
| same | af5c583 (build129) | 2108.8 ± 210.0 | 122.4 ± 0.3 |
| Qwen3-Coder-30B-A3B Q4, `-ncmoe 8` | v1.0.0, run 1 | 454.9 ± 10.5 | 48.5 ± 14.7 |
| same | af5c583, run 1 | 738.2 ± 18.0 | 36.4 ± 3.6 |
| same | v1.0.0, run 2 | 438.9 ± 25.5 | 35.0 ± 2.0 |
| same | af5c583, run 2 | 735.5 ± 10.3 | 30.5 ± 5.5 |

The pattern repeats on a second MoE family: v1.0.0 loses 38–41 % of prefill on `qwen3moe` with `-ncmoe` and gains only in decode, where the spread between runs (35 to 48 tok/s) is wider than the difference between builds. On the dense 7B both builds are level within noise, v1.0.0 slightly ahead on prefill.

**Verdict for our use.** Agent sessions and long prompts live on prefill, so `build129` (af5c583) stays the working build. Tag v1.0.0 is kept side by side in `build_v100` only for experiments that need the MoE expert cache.

**Environment note.** Both "server reboots" during this series were the Proxmox host OOM-killing the VM: it was configured with 118 784 MB on a 125 GiB host (`Out of memory: Killed process (kvm) anon-rss:115668044kB`). The VM now runs with 98 304 MB and balloon 2048. Also, v1.0.0 fails to build with the old flags alone: it needs `-DLLAMA_BUILD_UI=OFF` in addition to `-DLLAMA_BUILD_HTML=OFF`, otherwise the UI asset check aborts the build at 4 %.
