# V100-02 — q8_0 KV cache: how much context a 14B model gets in 16 GB

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Mixed.

**Question.** FP16 KV cache costs roughly 2 GB per 8k of context on a 14B model, which is what keeps 32k out of
a 16 GB card. Does quantizing the cache to q8_0 buy enough VRAM to reach 32k or 64k without offloading — and
does retrieval quality survive the quantization?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine | Ollama 0.40.16, FlashAttention on |
| Model | qwen2.5-14b-instruct, Q4 GGUF |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5, kernel 6.8.0-151 |
| Variables | `OLLAMA_KV_CACHE_TYPE` = f16 vs q8_0; `num_ctx` = 16384 / 32768 / 65536 |

**Commands** (request shape as issued; the driver script was not preserved). Ollama was restarted between the two
KV settings, because the variable is read at startup:

```bash
# f16 run
OLLAMA_KV_CACHE_TYPE=f16 OLLAMA_FLASH_ATTENTION=1 ollama serve
# q8_0 run
OLLAMA_KV_CACHE_TYPE=q8_0 OLLAMA_FLASH_ATTENTION=1 ollama serve

curl -s http://127.0.0.1:11434/api/generate -d '{
  "model": "qwen2.5-14b-instruct",
  "prompt": "<document of ~6500 tokens>",
  "stream": false,
  "options": {"num_ctx": 16384, "num_predict": 256, "temperature": 0}
}'
```

Retrieval check: three questions whose answers sit in the middle of the 6500-token document.

**Results.**

| num_ctx | KV cache | decode tok/s | VRAM peak, GB | needle test |
|---|---|---|---|---|
| 16384 | f16 | 21 | 13.6 | 3/3 |
| 16384 | q8_0 | 44 | 11.6 | 3/3 |
| 32768 | q8_0 | loads, not benchmarked | — | — |
| 65536 | q8_0 | does not load (OOM) | — | — |

**Repeats.** Single run per configuration, `n=1`. The 2x decode difference is larger than KV traffic alone
predicts, so the *direction* (q8_0 is not slower, and leaves ~2 GB free) is what these numbers support — the
exact size of the effect is not confirmed at `n=1`.

**Verdict.** Keep `q8_0` KV with FlashAttention on, and treat 32k as the practical ceiling for a 14B model on a
16 GB card. 64k does not fit at any KV precision, so the "64k on a V100" advice is worth ignoring rather than
retrying.

**Does not show.** Does not show why q8_0 doubles decode speed, and does not show the 32k case benchmarked at all — it loaded, nothing was measured. The needle test is three questions, not a retrieval benchmark. Both KV settings were measured once each in one session, so part of the 2x gap could be drift between Ollama restarts rather than the cache type.

**Raw.** `raw/runs/` has no file for this card — the run logs were not preserved.
