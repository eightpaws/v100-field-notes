# V100-02 — q8_0 KV cache: how much context a 14B model gets in 16 GB

_Measured on a Tesla V100-SXM2 16 GB (sm_70) in a Proxmox VM: 24 vCPU, 94 GiB RAM, driver 580.178.04._

**Result type.** Mixed.

**Question.** FP16 KV cache costs roughly 2 GB per 8k of context on a 14B model, which is what keeps 32k out of
a 16 GB card. Does quantizing the cache to q8_0 buy enough VRAM to reach 32k or 64k without offloading — and
does retrieval quality survive the quantization?

**Environment.**

| Component | Value |
|---|---|
| GPU / driver / compute cap | Tesla V100-SXM2-16GB, 16384 MiB / 580.178.04 / 7.0 (sm_70) |
| Engine, pass 1 | Ollama 0.40.16, FlashAttention on |
| Engine, pass 2 | llama.cpp `b1b770d` (1.0.0-dev), CUDA 12.9 |
| Model | qwen2.5-coder-14b, Q4_K_M GGUF (8 988 111 072 bytes) |
| Host | Proxmox VE VM — 24 vCPU (EPYC 7282), 94 GiB RAM, Ubuntu 24.04.5 |
| Variables | `OLLAMA_KV_CACHE_TYPE` = f16 vs q8_0; `num_ctx` = 16384 / 32768 / 65536; `-ctk/-ctv` = f16 vs q8_0, `-fa on` |

**Commands.** Pass 2, verbatim from the run log (`llama-bench` in this build has no `-c` flag; its context is
`n_prompt + n_gen`, so the speed runs are at 18 112 tokens):

```bash
llama-bench -m /models/qwen2.5-coder-14b.gguf -fa on -ctk f16  -ctv f16  -p 18048 -n 64 -ngl 99 -r 2 -o json
llama-bench -m /models/qwen2.5-coder-14b.gguf -fa on -ctk q8_0 -ctv q8_0 -p 18048 -n 64 -ngl 99 -r 2 -o json

# VRAM at full 32k context (KV allocated for the whole window):
llama-cli -m /models/qwen2.5-coder-14b.gguf -fa on -ctk q8_0 -ctv q8_0 -c 32768 -ngl 99 -n 64 -f prompt.txt
```

Pass 1 (Ollama, request shape as issued; the driver script was not preserved):

```bash
OLLAMA_KV_CACHE_TYPE=q8_0 OLLAMA_FLASH_ATTENTION=1 ollama serve
curl -s http://127.0.0.1:11434/api/generate -d '{
  "model": "qwen2.5-14b-instruct",
  "prompt": "<document of ~6500 tokens>",
  "stream": false,
  "options": {"num_ctx": 16384, "num_predict": 256, "temperature": 0}
}'
```

**Results.** Pass 2, llama.cpp, 18 048-token prompt, `n=2` per configuration:

| KV cache | prefill tok/s | decode tok/s | VRAM at 18k ctx, MiB | VRAM at 32k ctx, MiB |
|---|---|---|---|---|
| f16 | 1169.8 ± 0.9 | 70.6 ± 0.4 | 12 427 | 14 973 |
| **q8_0** | 1140.1 ± 0.3 | 67.6 ± 0.2 | 10 835 | 12 159 |

Pass 1, Ollama, ~6.5k prompt, `n=1` per configuration (kept for history):

| num_ctx | KV cache | decode tok/s | VRAM peak, GB | needle test |
|---|---|---|---|---|
| 16384 | f16 | 21 | 13.6 | 3/3 |
| 16384 | q8_0 | 44 | 11.6 | 3/3 |
| 32768 | q8_0 | loads, not benchmarked | — | — |
| 65536 | q8_0 | does not load (OOM) | — | — |

**Repeats.** Pass 2: `n=2` per configuration, llama-bench reports mean ± stdev (prefill 1169.8 ± 0.9 against
1140.1 ± 0.3; decode 70.6 ± 0.4 against 67.6 ± 0.2). The 32k VRAM figure is one load per KV type, with
`nvidia-smi` sampled every 300 ms and the maximum taken. Pass 1 was `n=1` and is not used for the decode numbers
any more.

**Verdict.** Quantizing the KV cache to q8_0 buys 2.75 GiB at 32k context — 12.16 GiB used instead of 14.97 —
for about 2.5 % prefill and 4.3 % decode, so 32k is reachable for a 14B model on a 16 GB card; take the
quantization for memory, not for speed, and 64k does not fit at any KV precision.

**Does not show.** Does not show the 64k case on llama.cpp (only Ollama was tried, and it failed to load), does
not re-run the needle test with a quantized cache at 32k, and measures prefill at zero depth, so the 32k figure
is memory only, not speed at depth. One model family, one host. The 2x decode gap recorded in pass 1 is not
reproduced here and is attributed to engine defaults rather than to the cache type.
